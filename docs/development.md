# Development

**Run every test and live experiment with an explicit throwaway `KATA_HOME`. Never point experiments at a normal store or a real project.** The root test runner creates a marked temporary root, clears inherited remote/issue routing, and passes isolated stores to the suites. Real-Kata fixtures stop their own daemons, and the runner stops any daemon left in its root when the tests end, including after Ctrl-C or SIGTERM. A run killed outright (SIGKILL) can't do that, so each run starts by stopping the daemons in roots whose runner is gone; a root whose runner is still running is left alone. A live experiment you start by hand leaves its daemon running: stop it with `KATA_HOME=<home> kata daemon stop`.

```sh
bun install --ignore-scripts
KATA_TEST_EXECUTABLE="$(readlink -f "$(command -v kata)")" bun run test
bun run check:plugins
bun run typecheck
```

The pi tests load Kata's real native pi adapter, never a fake: they install it with `kata agent-hook install`, which every supported Kata (0.23.0, the minimum, and later) has. `test` runs the OMP/pi, OpenCode and Claude Code adapter tests, real-Kata integration tests, and revision conformance. The adapter tests and every `smoke:*` script load the vendored copies in `plugins/*`, so every runner and every `smoke:*` script refuse to start until `bun run build:plugins` has refreshed them after a `core/` edit.

`bun run test` and `bun run test:files` run the test files in a pool of `bun test` processes, one file per process, longest known files first: `SLOW_FIRST` in `tests/run.ts` lists every file that takes over about 15 s, slowest first, then the rest follow alphabetically. A new slow file belongs in that list; left out, it starts last and stretches the run. A name in the list with no file behind it (a renamed test file) stops the run. `test:files` is `test` without revision conformance. The pool has 8 workers, or as many as the machine has CPUs when that is fewer; set `KATA_TEST_JOBS=<n>` to change that. `KATA_TEST_JOBS=1` runs every file in one streaming `bun test` process, the way to debug: output is live, not held until a file ends. Each worker has its own `KATA_HOME` (`home-<n>`) under the run's root, and every test file also makes its own scratch directory and store under `KATA_TEST_ROOT`, so no two files share a store. A file's output is printed whole when it finishes, followed by a summary of files passed and failed and the wall time; the run fails when any file does. Files named on the command line, `changed` and `revisions` run in a single process. A test must not rely on a fixed port, a file in the repo tree or anything else outside its own scratch directory, because another file may be running beside it.

A test file that needs a real Kata calls `realKata()` from `tests/kata-fixture.ts` once at its top. That gives it its own scratch directory, store and daemon, the `kata`, `text` and `show` helpers, and hooks that initialise the project, stop the daemon after the last test, and give every test the same `process.env`: each variable Kata routes by or the plugins read (`SCRUBBED_ENV` in `scripts/scrubbed-env.ts`, the list the runner and the smoke runners also clear) is removed before a test and put back after the file. A variable a test sets therefore never reaches the next test or, with `KATA_TEST_JOBS=1`, the next file; a plugin variable added to the code belongs in that list. The omp adapter's tests against a real Kata are split by area into `tests/v2-*.test.ts` (sessions, turn-end, delegate binding, hosted, tickets, forks and projects, guard-mirror and mirror-sessions), so the pool can spread them. Each file calls `v2Fixture()` from `tests/v2-fixture.ts` once, which adds the fake omp host and its helpers to `realKata()`. Add a test to the file for its area, and keep a file well under a minute so it does not become the pool's long pole. Pi's tests are split the same way into `tests/pi-*.test.ts` over `tests/pi-fixture.ts`. The two fake hosts share `fakeHost()` in `tests/kata-fixture.ts`; like the real hosts, it runs every handler registered for an event.

Pull requests run `.github/workflows/compatibility.yml`: a check of the vendored copies, the full `bun run test` and the typecheck (which covers `scripts/` and `tests/` too), against the public Kata 0.23.0 release in isolated homes. The check is `bun run check:plugins` and runs first: a copy in any plugin folder that is stale or missing fails the job before a test starts. Nothing regenerates the copies in CI, so the tests run the committed files, the same ones a release publishes. The runner has 4 CPUs and the suite keeps them all busy, so the workflow runs the test files in two parallel jobs: each sets `KATA_TEST_SHARD=<i>/2`, which deals the files in pool order to the two jobs, reversing direction each round so the slow files spread (`KATA_TEST_SHARD=<i>/<n>` works locally too, for runs of every file). The second job, which gets the lighter deal, also runs revision conformance and the typecheck. Pull requests that touch `core/`, `plugins/`, `scripts/`, `package.json`, `bun.lock` or `.github/actions/` also run `.github/workflows/omp-attention.yml`, which runs `bun run smoke:omp-attention` with real omp 19.1.1, the minimum the omp plugin supports: a Pi and an omp lead each start a native Pi from their bash tool, and the lead's attention must stay unchanged. Locally, set `OMP_BIN` and `PI_BIN` (defaults: `omp` on `PATH` and `node_modules/.bin/pi`). Both workflows install Bun and the Kata release through `.github/actions/setup-kata`, the one place that pins the two versions.

The `oxlint` and `tsrs` devDependencies are for the maintainer's local push gate (pr-gate). Its lint stage runs oxlint with type-aware rules and reports what it finds on the lines a branch adds. The gate takes oxlint from the primary checkout's `node_modules`, and oxlint finds tsrs, its type-aware backend, in the `node_modules` of the checkout being gated, so both are devDependencies rather than global installs. The oxlint config lives with the gate's files (`.agents/gate/oxlintrc.json`, linked in from outside this repo). tsrs implements the backend protocol oxlint drives, so after bumping either package, run the gate's lint stage once before relying on it.

Focused runners retain the isolation wrapper:

```sh
KATA_TEST_EXECUTABLE=/absolute/path/to/guarded-kata bun run test:files
KATA_TEST_EXECUTABLE=/absolute/path/to/guarded-kata bun run test:revisions
KATA_TEST_EXECUTABLE=/absolute/path/to/guarded-kata bun run test:changed        # vs the working tree
KATA_TEST_EXECUTABLE=/absolute/path/to/guarded-kata bun run test:changed main   # vs a branch or commit
```

`test:changed` is for the edit loop. It runs `bun test --changed`, which keeps only the test files whose imports reach a file git reports as changed: staged, unstaged and untracked files, plus commits since the ref when one is given. It cannot see what the tests reach without an import, so run `bun run test` before committing or closing a ticket. It misses:

- a `core/` edit until `bun run build:plugins` has refreshed the vendored copies the adapter tests import;
- files a test reads from disk, such as the manifests and changelog `packaging.test.ts` checks;
- `tests/revision-conformance.ts`, which runs outside `bun test`;
- a new Kata binary, which changes no file but is what most suites test.

The semantic canary copies the default database and WAL into a disposable directory. SQLite opens only that copy. It requires the same schema version, no new projects, and no new events from test actors or project names. Ordinary background sync and WAL/SHM churn are ignored. Unreadable, invalid, or unstable copies fail closed. Update fixture actor/project coverage in `tests/isolation.ts` when adding cases; never disable the canary to obtain a pass.

## Source layout

`core/kata-core.ts` holds the shared engine: plan state, transitions, ops and the host-facing API. `core/model.ts` holds the vocabulary every module shares (task, plan parent, Kata issue shape, qualified refs, the text of a host message, the mission marker and its close, the proof rule `PROOF_MIN`/`proofProblem` and `TITLE_MAX`). `core/kata-cli.ts` runs Kata: every call, its error envelope (`KataError`), the registered-project list refs are pinned against, the transcript environment of a close (`TRANSCRIPT_ENV`, `transcriptEnv`, `closeEnv`, which read the opt-out switch themselves), `CORE_ENV` (every variable the core reads, which is what `Platform.env.get` accepts), `debugTo` and `waitAtMost`. It also defines `Platform`, the seam for everything the core takes from its machine: environment (`env.get`/`env.set`, so a host with no process environment keeps the values and puts them on each call it makes), cwd, `path` (`PathOps`: `resolve`, `join`, `basename`, `dirname`), pid, timers (`Timers`), an async `realpath` and `appendFile`. Every path the core handles goes through `platform.path`: a Node host passes `node:path`, so Windows keeps its separators and drive letters, and a host without Node passes `posixPath` from `core/posix-path.ts`. `realpath` is required and asynchronous (a Node host wraps `fs.realpathSync`; any host gives the canonical path and rejects when nothing exists there); the core compares workspaces by `canonicalPath`, which resolves a file that does not exist yet through its folder. `core/shell.ts` and `core/plan-parent.ts` take the path operations as a parameter. The core imports nothing from Node: `core/sha256.ts` is the synchronous SHA-256 behind `digest` (idempotency keys must not change). `core/node-host.ts` is the one Node-only core module, imported by the Node adapters alone: `nodePlatform`, `sessionKey` (a session file's synchronous identity, for omp), `execKata` and `exportTranscriptSession`. `core/shell.ts` finds Kata invocations in a bash command, pins a delegate's to its teammate, puts a session's transcript pair before a close that lacks it (`transcriptCommand`, and in `delegateCommand`), and says whether a command is already routed. `core/autocomplete.ts` adds `#` ticket completion to the host's editor (`offerTickets`) and offers the same rows as `suggestTickets` for a host that draws its own menu. `core/plan-parent.ts` decides which plan parent and workspace a plan serves, as a pure function with no Kata calls. `core/todo-list.ts` compares the whole todo list a host sends with the Kata plan, with no Kata calls and no host. `core/delegates.ts` owns the delegate lifecycle, missions included, and `recordStore`, the delegate store a host backs with its own in-memory map; `core.delegate(id)` is a delegate's own core: the host's platform and options, never main, restoring nothing from the session's saved entries and saving nothing. The saved-entry rules a host's record follows are the core's too: `SavedEntry`, `withEntry` (the latest entry of each type, the only one the core reads), `savedSnapshot` and `holdsWork` (the session owes closes or has open tasks). `core/settlement.ts` owns the closes the plugin still owes a session: throttled task closes, ticket closes waiting on children and the automatic parent's close (closing first any mission its delegate's settle left open), with one drain, one timer, one snapshot and one verdict memory; its clock and timer are injected, so `tests/settlement.test.ts` drives time with a fake clock against real Kata. `core/inbox.ts` holds the session inbox: the trust rule, the `<kata_inbox>` render, the delivery text, and the live follower with its seed retry, head cache and restart backoff. The core builds the whole `kata events --tail` command, executable included, and a host only runs it: omp and Claude Code each supply a `LiveInbox` (`spawn(argv, cwd)` and `deliver(text)`); pi and OpenCode read the inbox per turn only. The prompt sections are named once, by `PROMPT_TAGS` and `tagged` in `core/kata-core.ts`. The adapters are `plugins/oh-my-pi/kata.ts`, `plugins/pi/kata.ts` and `plugins/opencode/kata.ts`. The core's messages name the host's own tool through the wording it is given (`ToolWording` in `core/model.ts`; omp and pi use the default). The OpenCode adapter is split into modules beside its `kata.ts`: `settings.ts` reads plugin options and the server's environment, `seam.ts` holds what the hooks share, `lead.ts` runs one lead session's core, `saved.ts` keeps its state in `ctx.storage`, `wording.ts` holds the `todowrite` tool's words, `todowrite.ts` is the `todowrite` tool, `subagents.ts` binds `subagent` calls to issues, `shell-route.ts` routes Kata commands in the `shell` tool, and `spawn.ts` runs a command for them. The Claude Code mod is `plugins/claude-code/hooks`: `register.ts` wires one hook per event, `lead.ts` makes the runtime and one session object per Claude session, `host.ts` builds the core's `Platform` and exec from the engine's `$` (the mod has no Node), `settings.ts` reads the options and `CORE_ENV`, `saved.ts` keeps `session/<id>` in `$.store`, `shell.ts` rewrites Kata closes in `Bash` and keeps their permission at `tool.check`, and `prompt.ts`, `todo.ts`, `delegates.ts`, `inbox.ts`, `lifecycle.ts`, `plan.ts` and `ui.tsx` are the hooks and the render state; `plugins/claude-code/types` holds the trimmed engine API (`claude-code.d.ts`) and the `$.state` contract. The Claude tests split in two: `tests/claude-*.test.ts` run the real hooks module over `tests/claude-fixture.ts`, a fake engine, against a real Kata, in `bun run test`; `plugins/claude-code/tests` run under `claude plugin test`. `bun run build:plugins` vendors into each plugin folder (`plugins/oh-my-pi`, `pi`, `opencode` and, for the Claude Code mod, `plugins/claude-code/core`) the core modules that folder's own files import, and the core modules those import in turn; each copy starts with a `// Generated from core/<name>; edit there.` line, `build:plugins` deletes a marked copy that no file reaches any more (its core module is gone or no longer imported), and `check:plugins` rejects a stale or orphaned copy. `scripts/vendor-core.ts` is run by plain `node` in the release workflow, so it stays erasable TypeScript. Each portable plugin's local imports stay inside its directory.

Kata failures are read from Kata's `--json` error envelope and exit code, never from message wording: the core adds `--json` to every call (except the contract hook) and branches on `daemon_unavailable` (exit 7), `project_not_initialized`, `sibling_throttle`, `parent_has_open_children` (the held close of a ticket), `unsupported_version` (a Kata older than the plugins use), `issue_not_found` (a deleted automatic parent, or a delegate's deleted issue, which the delegate's cleanup then drops) and `idempotency_deleted`/`idempotency_mismatch` on a keyed create (a deleted automatic parent is re-created under a derived key; an existing issue whose first create differed, for example one made by an earlier version whose priority came from the user's default, is adopted by the envelope's `data.qualified_id`). A missing executable or a killed call is detected from the exec result. The project name to register in an unregistered folder comes from the structured `data` on `project_not_initialized` (`project`, else `alias`), else the folder name; no code path reads a Kata message. Test fixtures in `tests/kata-errors.ts` are real Kata output.

Each serialized core job (a tool call, a session reload, a drain) is one Kata operation (`operation` in `core/kata-cli.ts`): a `kata show` with the same arguments is read once per operation, until any write through a runner on the same thread. Changes made elsewhere (a Kata command an agent runs in its shell, another process, an omp subagent's worker thread) show from the next operation on. A check that must see such a change inside one operation reads through `fresh`, as the automatic parent's audit does before it closes the parent. OpenCode's `todowrite` runs its view and every todo op it makes as one job (`todo.batch` in the core): one operation, with no delegate event, timer or other call of the session between them. Nothing in the core is ambient: a job (`Job` in `core/kata-cli.ts`) is passed down every call chain that started in it. It carries the context of the todo call it serves (so a Kata call keeps its own identity while another identity's event moves the core's latest context), the operation whose reads it reuses, and the batch it belongs to. A job a timer, event handler or poll starts itself is `NO_JOB`: its calls run with the latest context and read Kata every time, and a job held after its operation or batch ended behaves the same. `fresh(job)` gives the job a check that must read Kata again passes on. A job queued while a batch is open joins it only when it is queued with the batch's job: `todo.batch` hands that job to its function, which gives it to `todo.apply` and `delegates.check`; one queued without it waits for the whole batch and would deadlock it, so the job is a required last parameter of every public core method that queues one (`todo.apply`, `delegates.apply`, `start`, `check` and `restore`): a caller outside any job passes `NO_JOB` explicitly, and forgetting it is a compile error. The effective actor (`kata status`) is read once per session, workspace, project and `KATA_AUTHOR` value; the inbox's trust rule uses the same read. The read right after a claim stays: it stops a call when another writer marks the issue for a delegate right after the claim.

For live smoke tests, use a fresh Git folder and throwaway store as in the [tutorial](tutorials/first-session.md). Point `KATA_OMP_EXECUTABLE` or `KATA_PI_EXECUTABLE` at the guarded binary before launch. Inspect actual issues and close events; stop the test daemon and close any terminal panes you created. Keep transcripts and temporary reports outside the repository.

## Smoke test against a real omp

`bun run smoke:omp` loads `plugins/oh-my-pi/kata.ts` into a real, headless `omp -p` and checks the result in a real Kata daemon. Run it after each omp release and move the tested version in the README, `plugins/oh-my-pi/README.md` (the npm page) and install guide once it passes. It needs `omp` and `kata` on `PATH` and no credentials: a smoke-only extension (`scripts/smoke-omp-provider.ts`) registers a scripted model provider through `pi.registerProvider`, so the model calls are fixed. The same extension records each agent's system prompt as the plugin left it, the tool results each request carried (refusals included), and each finished tool call, with the thread the agent ran on; it loads in `--live` runs too. Every run selects the plugin's todo backend with a `--config` overlay (`todo.backend: kata`), so omp's own `todo` runs and the plugin mirrors and guards it; scripted `todo` calls send omp's own params only. Each run uses a fresh Git folder and a throwaway `KATA_HOME` (and, scripted, a throwaway `PI_CODING_AGENT_DIR`), set on the omp and Kata child processes only (your Kata store is never touched; live runs use your omp agent directory, see below), and stops its Kata daemon at the end, pass or fail. It prints one `PASS`/`FAIL` line per check and exits non-zero on any failure.

The default scenario checks that the first `todo init` is mirrored into an automatic parent with both plan tasks, that a `task` delegation binds to its plan task (the delegate's issue carries `omp.session_id` and, after it closed the issue and exited, `omp.status completed` with `omp.subagent_id` removed; the assignment proves omp's undocumented `task:subagent:lifecycle` payload still works), that `todo done` on the lead's task is refused while its Kata issue is open with a reason naming its ref, that the lead's own `kata close` records the evidence and the omp session, that `todo done` then goes through, and that session shutdown closes the automatic parent with the same session; with `--live` it also checks that the delegate commented on its own task under the teammate the issue carried when it closed, not counting the report the plugin posts for it. Close and `done` are separate turns in every script: omp runs a message's `tool_call` handlers before any of its calls, so a `done` sharing a message with its close is refused. A scripted turn waits for the mirror inside omp's `bash` tool (a `bun -e` script that polls `kata list` for the plan task's issue), because the mirror runs after omp's `todo` call returns. The `fork` scenario forks the session over RPC and checks that the fork's plan changes land under the source's parent. The `tickets` scenario covers ticket-named plan items: `done` on an item that is not its ticket's last open item goes through and comments on the ticket, `done` on the last one is refused until the agent closes the ticket with `kata close` (its only close), an item naming a missing ticket creates nothing, dropping an item leaves its ticket open, and a delegate that closes its ticket has it returned to the lead. The `claimed` scenario has the agent claim a ticket with `kata claim`, which makes it the plan parent, and plan a ticket item and a plain item under it; the agent closes the plain item's issue, then the ticket, and the scenario checks that the ticket closed once, through that `kata close`, with the ticket item's evidence. The `untracked` scenario sends a `scout` that matches no plan item and checks that its run leaves one mission (closed as `audit-no-change`, `omp.mission_agent` `scout`, its report under its teammate) and no `needs-review` label or inbox request, and that the automatic parent still closes as done from the plan's own items, each closed with `kata close` before its `done`. The `workers` scenario delegates fourteen plan tasks in one `task` call, enough for omp to run several delegates on a worker thread, and checks that every delegate's prompt names its own plan task. `workers-slow-kata` (scripted only) repeats it with the plugin's Kata executable set to `scripts/smoke-slow-kata.sh`, which starts every call 25 ms late (`KATA_SMOKE_DELAY`) as a loaded machine would, so the fourteen assignments take several seconds and the last delegate's first prompt has to wait for them. Scripted, each delegate closes its issue with `kata close`, runs `ls` and leaves it open, or answers without a tool; delegates on a worker thread take these roles in turn in the order they started, the others by number. It checks that each task was closed, handed back (`needs-review`, `work.attention needs-human`, an inbox request) or rolled back (open, unlabelled, no `omp.subagent_id`) to match, and that every role had a delegate on a worker thread. The scripted lead only acknowledges each delegate's report; the end of that turn waits for the hand backs and rollbacks (`TURN_SETTLE_MS`), because omp gives `session_shutdown` only 2 s, too little to write them all at exit. With `--live`, odd-numbered delegates plan one step under their own issue with `todo`, close that step's issue with `kata close`, mark it done, then close their own issue with `kata close`, and even-numbered ones run `ls` and leave their task open. omp strips its `todo` tool from subagents unless prewalk is armed, so the scenario adds a `task.agentPrewalk` target (a subscription model) to the `--config` overlay (scenario field `ompConfig`, appended after `todo.backend: kata`); prewalk only hands off at a delegate's first edit, which these never make. For the delegates omp ran on a worker thread, it checks that an odd one's `todo` and `kata close` worked and both closes record its own session, and that an even one was handed back (`needs-review`, `work.attention needs-human`, an inbox request); each kind has to land on a worker at least once. Under prewalk a real model tends to add steps and work of its own, so a live run can fail on model behaviour or hit the 10-minute limit; read the failure detail before suspecting the plugin.

The `resume` scenario (scripted only) persists the lead's session and delegates two plan tasks: one delegate finishes a `bash` call and starts a long one, the other is still waiting on its first model call (a scripted `{ hang: true }` turn that never answers). The driver SIGKILLs omp once the lead's snapshot records the first delegate's tool use (no shutdown hook runs, so neither delegate is cleaned up) and checks that both issues are still held (`omp.subagent_id`, `omp.status running`). It then resumes the same session file with `omp --resume <file>` and sends one short lead turn, which waits in omp's `bash` tool until the background settle has written both cleanups (omp's own `todo view` no longer passes through the plugin, so it cannot wait for them). It checks that the delegate that ran a tool was handed back (`needs-review`, `work.attention needs-human`, an inbox request, `omp.status aborted`), the other rolled back (open, unlabelled, no `omp.subagent_id`), and that no stray issue exists.

The `identity-shim` scenario (scripted only) runs omp's `bash` as `/bin/bash` with a recording `kata` ahead of the real one on `PATH`, also put first again by `.bash_profile` as a shell rc file would. The lead exports a forged `KATA_AUTHOR` and `KATA_TEAMMATE` before its own `kata comment`, then delegates the fourteen `workers` tasks; each delegate exports forged identity variables, comments through `bash -c` and through a script, and closes its issue through `bash -c`. It checks that the lead's comment carries the session's actor and no teammate, that each delegate's two comments carry the actor and one unforged teammate and its close records the delegate's own session, that the provider history shows those commands without `--teammate`, that each delegate has a recorded call whose inbox user is its own `<actor>/<teammate>` (the lead's calls keep the launch `KATA_INBOX_USER`, or none, and are not checked), and that at least one delegate's `bash` ran on a worker thread.

```sh
bun run smoke:omp                       # every scenario, scripted model
bun run smoke:omp --scenario default    # one scenario
bun run smoke:omp --verbose             # also print omp's JSON event stream
bun run smoke:omp --live --model anthropic/<model>    # same checks with a real model (prefer a subscription)
```

The `inbox` and `inbox-per-turn` scenarios drive one long-lived `omp --mode rpc` session, running `kata notify` against the throwaway store (the notify sender and the session share `KATA_AUTHOR`, so the trust rule accepts it) and checking what the scripted provider recorded per request. `inbox` checks live delivery with no prompt: a notify starts a turn on an idle agent (the delivered text names the sender, the issue and how to clear it), reaches a working agent (a scripted slow `bash` step) after its tool result without interrupting it, is delivered once, and a clear delivers nothing; the `<kata_inbox>` section shows the request on the next prompt and drops it after the clear. It also sends a request as another actor (`KATA_AUTHOR=mallory`, a forged sender) and checks that it starts no turn and its text reaches no system prompt or user message. `inbox-per-turn` runs with `KATA_OMP_LIVE_INBOX=0`: nothing is delivered live, the request must appear as `<kata_inbox>` within two turns (a read slower than the hook's budget lands on the next turn) and disappear within two turns of clearing it. Both are scripted-only and skipped by `--live`.

Scenarios are data in `scripts/smoke-omp-scenarios.ts`: scripted turns per agent (a turn may be a function of the conversation so far) plus assertions over the store. Add one by appending an entry to `SCENARIOS`; a scenario that only scripts turns and checks the store needs no driver or provider changes. One that needs a new RPC command or a persisted session (like `fork`) also extends the driver, and one that restarts omp (`restart`: kill and `--resume`, like `resume`) or needs a model call that never answers (`{ hang: true }`) relies on the driver's restart and the provider's hang turn. An agent runs the script keyed by the longest marker its first user message contains (`pickTurn` in `scripts/smoke-provider.ts`, which the OpenCode provider uses too), so one marker may extend another. `scripts/smoke-lib.ts` holds what the smoke runners share: the throwaway root, the Kata project of a scenario, the child processes and the report. An interrupted run (Ctrl-C) still stops its host and its Kata daemon and removes the root.

`--live` has the real model do the work from a plain-language prompt, so it needs a login. Scripted runs give omp a throwaway `PI_CODING_AGENT_DIR`; live runs use your own (an inherited `PI_CODING_AGENT_DIR`, else `~/.omp/agent`) with its logins and settings, so a subscription login works and refreshes in place, and omp may update that directory as in any run. The Kata store stays a throwaway one. Prefer a subscription model for `--model` over a pay-per-use API key. A scenario's omp settings (`ompConfig`) go in as a `--config` overlay for the run, never into your `config.yml`. Live runs spend tokens or subscription quota and can fail on model behaviour rather than plugin behaviour; the `workers` scenario runs 14 delegates and can take the full 10 minutes.

## Smoke test against a real OpenCode

`bun run smoke:opencode` loads `plugins/opencode` into a real, headless `opencode run --standalone` and checks the result in a real Kata daemon. It runs locally only and is not part of CI. Run it before each release and after each OpenCode release, and move the tested version in the README and install guide once it passes. It needs `opencode` and `kata` on `PATH` and no credentials: `scripts/smoke-opencode-provider.ts` starts a scripted OpenAI-compatible model provider in the same process, so the model calls are fixed. Each run uses a fresh Git folder, a throwaway `KATA_HOME` and throwaway `HOME` and `XDG_*` directories. OpenCode loads the repo's `plugins/opencode` folder itself (its `package.json` `exports` names `kata.ts`), listed in the folder's `opencode.json` with the scenario's plugin options. The `shared-server` scenario instead starts one `opencode serve` (with a throwaway password, which `opencode run --server` must present) and runs two leads against it at once, in a folder with no Kata project and with the `defaultProject` plugin option as the only routing; it checks that each lead gets its own automatic parent in that project and that closes carry the right session.

```sh
bun run smoke:opencode                       # every scenario
bun run smoke:opencode --scenario plan       # one scenario
bun run smoke:opencode --verbose             # also print OpenCode's JSON event stream
```

Scenarios are data in `scripts/smoke-opencode.ts`: scripted turns per agent (keyed by a marker in the agent's first user message; the longest marker it contains wins) plus assertions over the store. Add one by appending an entry to `SCENARIOS`; the driver changes only for a scenario that restarts OpenCode. `shared-server` is the exception: it is not a `SCENARIOS` entry but has its own driver (`runShared`, which starts `opencode serve` and two `opencode run --server` leads), and `--scenario shared-server` (and the default run) is special-cased in the script's main block.

## Smoke test against a real Claude Code

`bun run smoke:claude` loads `plugins/claude-code` into a real, headless `claude -p --model haiku --plugin-dir plugins/claude-code` and checks the result in a real Kata daemon. It runs in the default permission mode with `Bash(kata *)` and the plain file checks allowed, so a rewritten `kata close` that loses that rule's permission is refused and fails the run. **It is paid and needs a login**: Claude Code has no scripted model provider, so a real model does the work, and the run spends a few cents of subscription usage or API credit (`--model <name>` picks another model; the script stops at a spend of 1 USD). It runs locally only and is not part of CI, which does not install Claude Code. Run it before a Claude release and after each Claude Code release, and move the tested version in the README, `plugins/claude-code/README.md` (the plugin directory listing), the install guide, the reference, `docs/explanation/limits.md` and the header of `plugins/claude-code/types/claude-code.d.ts` once it passes. It needs `claude` (logged in) and `kata` on `PATH`. Each run uses a fresh Git folder and a throwaway `KATA_HOME`; Claude Code itself uses your own config directory and its login, so it may update that directory as in any run.

The prompt has the model plan two tasks with the `todo` tool, do and close the first itself, hand the second to an `Agent` subagent, then create and close an issue with `kata` in `Bash`. The run passes when `claude` exits 0 and the store holds exactly one automatic parent carrying the session id, with both tasks under it; the first closed with evidence and a transcript naming agent `claude` and the session id; the second bound to the subagent (its issue carries the lead's session) and closed by it once, with evidence, a comment of its own (not the report the plugin posts for it) and the lead's transcript, then returned to the lead (no subagent id left on it); the `Bash` issue closed with the lead's transcript; no task handed back for review; and the parent closed at session end, once, with a transcript naming agent `claude`. A model can fail the run without the plugin being at fault; a failed run prints the store and Claude Code's last output to tell the two apart.

```sh
bun run smoke:claude                 # paid: one headless run on haiku
bun run smoke:claude --model sonnet  # another model
bun run smoke:claude --verbose       # also print Claude Code's output
bun run validate:claude              # claude plugin validate, free
bun run test:claude                  # claude plugin test, free
```

`validate:claude` and `test:claude` need no login and call no model, but need Claude Code on `PATH`, so CI does not run them either. Run both before a Claude release.

## Changelog

Each plugin keeps a `CHANGELOG.md` in its folder (`plugins/pi`, `plugins/oh-my-pi`, `plugins/opencode`, `plugins/claude-code`) that follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Its release sections are that plugin's release notes, and its npm package ships it. The root `CHANGELOG.md` only links the four.

- **When:** in the commit that makes a change a user can notice. The entry goes under `## [Unreleased]`, in `### Added`, `### Changed`, `### Removed` or `### Fixed` (that order); add the subsection when it is missing.
- **Which plugins:** a change inside one plugin's folder goes in that plugin's changelog. A change in `core/` goes in the changelog of every plugin it reaches (`bun run build:plugins` copies each core module into the plugins that import it), worded in that host's terms: `todo` or `todowrite`, `task`, `subagent` or `Agent`. Tooling every plugin shares (the test runner, CI, the gate) gets no entry.
- **Area:** inside each type, entries sit under a `####` area heading, in this order: Requirements (Kata and host versions), Install and update, Plans (the `todo` tool, parents, ticket items, closes), Delegates, Inbox and attention, Repository content (what the plugin refuses to write into the repo), Display (the `#` menu, widgets, Tern), Development (the plugin's own scripts and checks). Add a heading only when the type has an entry for that area; a new area joins this list first.
- **Shape:** one feature or fix per top-level bullet, a sentence that names the thing that changed. Detail goes in sub-bullets of a line or two each. A change that breaks an upgrade starts with `**Breaking:**` and says what to do.
- **Reader:** someone who installs and uses the plugins. Write in the present tense, and name the behaviour, not ticket ids or commit hashes.
- **Credit:** an entry for a change someone other than the maintainer contributed ends its top-level bullet with `Thanks to @<user> ([#<pr>](<pull request URL>)).`, the one place a changelog entry links a pull request. When one contributor made every change in a release, say so once on the line under the version heading instead.
- **Superseded:** when later work replaces something already under Unreleased, rewrite that entry in its final form.

## Releases

Installs come from the marketplaces (`kata@kata-plugin` in omp, `kata-cc@kata-plugin` in Claude Code), Git, and npm: `@dangerboi/kata-pi`, listed in the [Pi package gallery](https://pi.dev/packages) through its `pi-package` keyword, and `@dangerboi/kata-omp`, listed on [omp packages](https://omppackages.com) through its `omp-plugin` keyword (the catalog reads npm and takes up to about six hours to show a new version). npm refuses the unscoped name `kata-pi` as too close to an existing package. The OpenCode package is `@dangerboi/kata-opencode`. The marketplace registers the omp plugin under its package name too, so a marketplace install and an npm install share one slot in omp.

Each package releases on its own tag: `pi-v<version>`, `omp-v<version>`, `opencode-v<version>` and `claude-code-v<version>`. A release never carries another package with it, so a change in `core/` reaches each package with that package's next release. Up to kata-plugin 1.12.0, `v<version>` tags released pi and omp together; each of those release commits also carries the `pi-v` and `omp-v` tags its changelogs link. The workflow no longer runs for `v*` tags. To release a plugin:

1. Bump its `version`: in `plugins/<plugin>/package.json`, or for Claude Code in `plugins/claude-code/.claude-plugin/plugin.json` and the `kata-cc` entry of `.claude-plugin/marketplace.json` (`tests/packaging.test.ts` fails when those two differ). A pi release also sets the root `package.json` version to pi's: the root manifest is what `pi install git:…` installs.
2. In the plugin's `CHANGELOG.md`, rename `## [Unreleased]` to `## [<version>] - YYYY-MM-DD` and put a new empty `## [Unreleased]` above it. At the end of the file, point `[Unreleased]` at `https://github.com/Dangerboi/kata-plugin/compare/<tag>...HEAD` and add `[<version>]: https://github.com/Dangerboi/kata-plugin/compare/<previous tag>...<tag>`. Claude Code's first release links `https://github.com/Dangerboi/kata-plugin/releases/tag/claude-code-v<version>` instead. `tests/packaging.test.ts` fails when the newest release heading is not the manifest's version. Pi shows a package's new changelog entries after an update and reads only `##` headings that start with a version, brackets allowed; it compares that version with the installed package's.
3. After the change merges, tag `main` as `<plugin>-v<version>` and publish a GitHub release from that tag with the changelog section as its notes.
4. Pushing a `pi-v`, `omp-v` or `opencode-v` tag publishes that package: `.github/workflows/publish-pi.yml` runs `npm publish` in its folder through npm [trusted publishing](https://docs.npmjs.com/trusted-publishers) (OIDC), so no npm token or one-time code is involved. Each of the jobs `publish-pi`, `publish-omp` and `publish-opencode` runs only for its own tag prefix, fails when the tag does not name its package's version, and skips a version already on npm. To publish an existing tag again, run the workflow by hand: `gh workflow run publish-pi.yml -f tag=<tag>`. npm trusts the workflow by its file name; each package's trusted publisher on npmjs.com (package settings, Trusted publishing) names `Dangerboi/kata-plugin` and `publish-pi.yml` and allows `npm publish`, so renaming the file stops publishing. `publishConfig` makes the scoped packages public. Their `prepack` copies the root `LICENSE` into the package and `postpack` removes it again; `npm pack --dry-run` lists the files without publishing. The gallery preview, `pi.image` (and `pi.video`, if set), points at `docs/media/` on `main`, so a new preview shows once it is merged.
5. A trusted publisher is a package setting, so a new npm package must exist before it can have one: publish its first version by hand from its folder (`npm publish --access public`, signed in as the maintainer), add the trusted publisher on npmjs.com, then push the version's tag so later compare links have a base; the job skips the version as already on npm.
6. OpenCode loads its package through `exports["."]` (`./kata.ts`), and a folder with the same manifest loads the same way, so `tests/packaging.test.ts` checks the manifest, the tarball and the local import graph.
7. Claude Code's `kata-cc` has no npm package and no publish job, and its `claude-code-v` tag only marks the release: `/plugin install kata-cc --marketplace Dangerboi/kata-plugin` reads `.claude-plugin/marketplace.json` and the plugin folder from the repository's Git, and a local-folder marketplace reads `plugins/claude-code` in place. Claude Code pins an install to the plugin's `version`, so a change reaches an installed copy only when the version moves.
   1. Before the release, run `bun run validate:claude`, `bun run test:claude` and `bun run smoke:claude` (paid), and move the tested Claude Code version in the README, `plugins/claude-code/README.md`, the install guide, the reference, `docs/explanation/limits.md` and the header of `plugins/claude-code/types/claude-code.d.ts` when the host moved.
   2. After the change merges to `main`, users pick it up with `claude plugin marketplace update kata-plugin` and `claude plugin update kata-cc@kata-plugin`, then `/reload-plugins`.
