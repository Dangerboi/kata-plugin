# Development

**Run every test and live experiment with an explicit throwaway `KATA_HOME`. Never point experiments at a normal store or a real project.** The root test runner creates a marked temporary root, clears inherited remote/issue routing, and passes isolated stores to the suites. Real-Kata fixtures stop their own daemons, and the runner stops any daemon left in its root when the tests end, including after Ctrl-C or SIGTERM. A run killed outright (SIGKILL) can't do that, so each run starts by stopping the daemons in roots whose runner is gone; a root whose runner is still running is left alone. A live experiment you start by hand leaves its daemon running: stop it with `KATA_HOME=<home> kata daemon stop`.

```sh
bun install --ignore-scripts
KATA_TEST_EXECUTABLE="$(readlink -f "$(command -v kata)")" bun run test
bun run check:plugins
bun run typecheck
```

The real native pi adapter tests need Kata 0.23.0, the minimum version; they are skipped when `kata agent-hook install` is missing, never faked. `test` runs OMP/pi tests, real-Kata integration tests, and revision conformance. The adapter tests and `smoke:omp` load the vendored copies in `plugins/*`, so every runner and `smoke:omp` refuse to start until `bun run build:plugins` has refreshed them after a `core/` edit.

Pull requests run `.github/workflows/compatibility.yml`: the full `bun run test`, the typecheck and a drift check of the vendored copies, against the public Kata 0.23.0 release in isolated homes. Pull requests that touch `core/`, `plugins/`, `package.json`, `scripts/smoke-omp-attention.ts` or `scripts/smoke-provider.ts` also run `.github/workflows/omp-attention.yml`, which runs `bun run smoke:omp-attention` with real omp 18.18.1 and 18.18.6: a Pi and an omp lead each start a native Pi from their bash tool, and the lead's attention must stay unchanged. Locally, set `OMP_BIN` and `PI_BIN` (defaults: `omp` on `PATH` and `node_modules/.bin/pi`).

Focused runners retain the isolation wrapper:

```sh
KATA_TEST_EXECUTABLE=/absolute/path/to/guarded-kata bun run test:todo
KATA_TEST_EXECUTABLE=/absolute/path/to/guarded-kata bun run test:revisions
KATA_TEST_EXECUTABLE=/absolute/path/to/guarded-kata bun run test:changed        # vs the working tree
KATA_TEST_EXECUTABLE=/absolute/path/to/guarded-kata bun run test:changed main   # vs a branch or commit
```

`test:changed` is for the edit loop. It runs `bun test --changed`, which keeps only the test files whose imports reach a file git reports as changed: staged, unstaged and untracked files, plus commits since the ref when one is given. It cannot see what the tests reach without an import, so run `bun run test` before committing or closing a ticket. It misses:

- a `core/` edit until `bun run build:plugins` has refreshed the vendored copies the adapter tests import;
- files a test reads from disk, such as the manifests and changelog `packaging.test.ts` checks;
- `tests/revision-conformance.ts`, which runs outside `bun test`;
- a new Kata binary, which changes no file but is what most suites test.

The semantic canary copies the default database and WAL into a disposable directory. SQLite opens only that copy. It requires the same schema version, no new projects, and no new events from test actors or project names. Ordinary background sync and WAL/SHM churn are ignored. Unreadable, invalid, or unstable copies fail closed. Update fixture actor/project coverage in `tests/isolation.ts` when adding cases; never disable the canary to obtain a pass.

## Source layout

`core/kata-core.ts` holds the shared engine: plan state, transitions, ops and the host-facing API. `core/model.ts` holds the vocabulary every module shares (task, plan parent, Kata issue shape, qualified refs, the text of a host message). `core/kata-cli.ts` runs Kata: every call, its error envelope (`KataError`) and the registered-project list refs are pinned against. `core/shell.ts` finds Kata invocations in a bash command and pins a delegate's to its teammate. `core/autocomplete.ts` adds `#` ticket completion to the host's editor. `core/plan-parent.ts` decides which plan parent and workspace a plan serves, as a pure function with no Kata calls. `core/delegates.ts` owns the delegate lifecycle. `core/settlement.ts` owns the closes the plugin still owes a session: throttled task closes, ticket closes waiting on children and the automatic parent's close, with one drain, one timer, one snapshot and one verdict memory; its clock and timer are injected, so `tests/settlement.test.ts` drives time with a fake clock against real Kata. `core/inbox.ts` holds the session inbox: the trust rule, the `<kata_inbox>` render, the delivery text, and the live follower with its seed retry, head cache and restart backoff. The omp adapter spawns `kata events --tail` and hands that to the follower through its dependencies; pi reads the inbox per turn only. The adapters are `plugins/oh-my-pi/kata.ts` and `plugins/pi/kata.ts`. `bun run build:plugins` vendors every `core/*.ts` module into both plugin folders; `check:plugins` rejects a stale copy. Each portable plugin's local imports stay inside its directory.

Kata failures are read from Kata's `--json` error envelope and exit code, never from message wording: the core adds `--json` to every call (except the contract hook) and branches on `daemon_unavailable` (exit 7), `project_not_initialized`, `sibling_throttle`, `issue_not_found` (a deleted automatic parent, or a delegate's deleted issue, which the delegate's cleanup then drops) and `idempotency_deleted`/`idempotency_mismatch` on a keyed create (a deleted automatic parent is re-created under a derived key; an existing issue whose first create differed, for example one made by an earlier version whose priority came from the user's default, is adopted by the envelope's `data.qualified_id`). A missing executable or a killed call is detected from the exec result. The project name to register in an unregistered folder comes from the structured `data` on `project_not_initialized` (`project`, else `alias`), else the folder name; no code path reads a Kata message. Test fixtures in `tests/kata-errors.ts` are real Kata output.

For live smoke tests, use a fresh Git folder and throwaway store as in the [tutorial](tutorials/first-session.md). Point `KATA_OMP_EXECUTABLE` or `KATA_PI_EXECUTABLE` at the guarded binary before launch. Inspect actual issues and close events; stop the test daemon and close any terminal panes you created. Keep transcripts and temporary reports outside the repository.

## Smoke test against a real omp

`bun run smoke:omp` loads `plugins/oh-my-pi/kata.ts` into a real, headless `omp -p` and checks the result in a real Kata daemon. Run it after each omp release and move the tested version in the README and install guide once it passes. It needs `omp` and `kata` on `PATH` and no credentials: a smoke-only extension (`scripts/smoke-omp-provider.ts`) registers a scripted model provider through `pi.registerProvider`, so the model calls are fixed. The same extension records each agent's system prompt as the plugin left it and each finished tool call, with the thread the agent ran on; it loads in `--live` runs too. Each run uses a fresh Git folder and a throwaway `KATA_HOME` (and, scripted, a throwaway `PI_CODING_AGENT_DIR`), set on the omp and Kata child processes only (your Kata store is never touched; live runs use your omp agent directory, see below), and stops its Kata daemon at the end, pass or fail. It prints one `PASS`/`FAIL` line per check and exits non-zero on any failure.

The default scenario checks that `todo init` creates the automatic parent and its plan tasks, that a `task` delegation binds to its plan task (the delegate's issue carries `omp.session_id` and, after it closed the issue and exited, `omp.status completed` with `omp.subagent_id` removed; the assignment proves omp's undocumented `task:subagent:lifecycle` payload still works), that `todo done` closes with the given evidence and comments its message and evidence, and that session shutdown closes the automatic parent; with `--live` it also checks that the delegate commented on its own task under the teammate the issue carried when it closed, not counting the report the plugin posts for it. The `fork` scenario forks the session over RPC and checks that the fork's plan changes land under the source's parent. The `tickets` scenario covers ticket-named plan items, including a delegate that closes its ticket, which the plugin then returns to the lead. The `untracked` scenario sends a `scout` that matches no plan item and checks that it creates no issue, `needs-review` label or inbox request, and that the automatic parent still closes from the plan's own items. The `workers` scenario delegates fourteen plan tasks in one `task` call, enough for omp to run several delegates on a worker thread, and checks that every delegate's prompt names its own plan task. `workers-slow-kata` (scripted only) repeats it with the plugin's Kata executable set to `scripts/smoke-slow-kata.sh`, which starts every call 25 ms late (`KATA_SMOKE_DELAY`) as a loaded machine would, so the fourteen assignments take several seconds and the last delegate's first prompt has to wait for them. Scripted, each delegate closes its issue with `kata close`, runs `ls` and leaves it open, or answers without a tool; delegates on a worker thread take these roles in turn in the order they started, the others by number. It checks that each task was closed, handed back (`needs-review`, `work.attention needs-human`, an inbox request) or rolled back (open, unlabelled, no `omp.subagent_id`) to match, and that every role had a delegate on a worker thread. The scripted lead only acknowledges each delegate's report; the end of that turn waits for the hand backs and rollbacks (`TURN_SETTLE_MS`), because omp gives `session_shutdown` only 2 s, too little to write them all at exit. Scripted worker delegates need omp 18.18 or later; 18.17 fails every model call a worker-thread subagent makes through an extension's provider. With `--live`, odd-numbered delegates plan one step under their own issue with `todo`, finish it, then close their issue with `kata close`, and even-numbered ones run `ls` and leave their task open. omp strips its `todo` tool from subagents unless prewalk is armed, so the scenario passes a `task.agentPrewalk` target (a subscription model) as a `--config` overlay (scenario field `ompConfig`); prewalk only hands off at a delegate's first edit, which these never make. For the delegates omp ran on a worker thread, it checks that an odd one's `todo` and `kata close` worked and both closes record its own session, and that an even one was handed back (`needs-review`, `work.attention needs-human`, an inbox request); each kind has to land on a worker at least once. Under prewalk a real model tends to add steps and work of its own, so a live run can fail on model behaviour or hit the 10-minute limit; read the failure detail before suspecting the plugin.

The `resume` scenario (scripted only) persists the lead's session and delegates two plan tasks: one delegate finishes a `bash` call and starts a long one, the other is still waiting on its first model call (a scripted `{ hang: true }` turn that never answers). The driver SIGKILLs omp once the lead's snapshot records the first delegate's tool use (no shutdown hook runs, so neither delegate is cleaned up) and checks that both issues are still held (`omp.subagent_id`, `omp.status running`). It then resumes the same session file with `omp --resume <file>`, sends one short lead turn, and checks that the delegate that ran a tool was handed back (`needs-review`, `work.attention needs-human`, an inbox request, `omp.status aborted`), the other rolled back (open, unlabelled, no `omp.subagent_id`), and that no stray issue exists.

```sh
bun run smoke:omp                       # every scenario, scripted model
bun run smoke:omp --scenario default    # one scenario
bun run smoke:omp --verbose             # also print omp's JSON event stream
bun run smoke:omp --live --model anthropic/<model>    # same checks with a real model (prefer a subscription)
```

The `inbox` and `inbox-per-turn` scenarios drive one long-lived `omp --mode rpc` session, running `kata notify` against the throwaway store (the notify sender and the session share `KATA_AUTHOR`, so the trust rule accepts it) and checking what the scripted provider recorded per request. `inbox` checks live delivery with no prompt: a notify starts a turn on an idle agent (the delivered text names the sender, the issue and how to clear it), reaches a working agent (a scripted slow `bash` step) after its tool result without interrupting it, is delivered once, and a clear delivers nothing; the `<kata_inbox>` section shows the request on the next prompt and drops it after the clear. It also sends a request as another actor (`KATA_AUTHOR=mallory`, a forged sender) and checks that it starts no turn and its text reaches no system prompt or user message. `inbox-per-turn` runs with `KATA_OMP_LIVE_INBOX=0`: nothing is delivered live, the request must appear as `<kata_inbox>` within two turns (a read slower than the hook's budget lands on the next turn) and disappear within two turns of clearing it. Both are scripted-only and skipped by `--live`.

Scenarios are data in `scripts/smoke-omp-scenarios.ts`: scripted turns per agent (a turn may be a function of the conversation so far) plus assertions over the store. Add one by appending an entry to `SCENARIOS`; a scenario that only scripts turns and checks the store needs no driver or provider changes. One that needs a new RPC command or a persisted session (like `fork`) also extends the driver, and one that restarts omp (`restart`: kill and `--resume`, like `resume`) or needs a model call that never answers (`{ hang: true }`) relies on the driver's restart and the provider's hang turn.

`--live` has the real model do the work from a plain-language prompt, so it needs a login. Scripted runs give omp a throwaway `PI_CODING_AGENT_DIR`; live runs use your own (an inherited `PI_CODING_AGENT_DIR`, else `~/.omp/agent`) with its logins and settings, so a subscription login works and refreshes in place, and omp may update that directory as in any run. The Kata store stays a throwaway one. Prefer a subscription model for `--model` over a pay-per-use API key. A scenario's omp settings (`ompConfig`) go in as a `--config` overlay for the run, never into your `config.yml`. Live runs spend tokens or subscription quota and can fail on model behaviour rather than plugin behaviour; the `workers` scenario runs 14 delegates and can take the full 10 minutes.

## Changelog

`CHANGELOG.md` follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and its release sections are the release notes.

- **When:** in the commit that makes a change a user can notice. The entry goes under `## [Unreleased]`, in `### Added`, `### Changed`, `### Removed` or `### Fixed` (that order); add the subsection when it is missing.
- **Area:** inside each type, entries sit under a `####` area heading, in this order: Requirements (Kata and host versions), Install and update, Plans (the `todo` tool, parents, ticket items, closes), Delegates, Inbox and attention, Display (the `#` menu, widgets, Tern), Development. Add a heading only when the type has an entry for that area; a new area joins this list first.
- **Shape:** one feature or fix per top-level bullet, a sentence that names the thing that changed. Detail goes in sub-bullets of a line or two each. A change that only one host gets starts with `omp:` or `pi:`. A change that breaks an upgrade starts with `**Breaking:**` and says what to do.
- **Reader:** someone who installs and uses the plugins. Write in the present tense, and name the behaviour, not ticket ids or commit hashes.
- **Superseded:** when later work replaces something already under Unreleased, rewrite that entry in its final form.

## Releases

Installs come from the marketplace (`kata@kata-plugin`), Git, and npm for pi (`@dangerboi/kata-pi`, listed in the [Pi package gallery](https://pi.dev/packages) through its `pi-package` keyword). npm refuses the unscoped name `kata-pi` as too close to an existing package. `kata-omp` is not published.

1. Bump `version` by hand in each changed plugin's `plugins/*/package.json`. Keep the root `package.json` version equal to pi's: the root manifest is what `pi install git:…` installs.
2. In `CHANGELOG.md`, rename `## [Unreleased]` to `## [<root version>] - YYYY-MM-DD`, start the section with a line naming both plugin versions (`kata-omp 2.7.0 and @dangerboi/kata-pi 1.7.1.`), and put a new empty `## [Unreleased]` above it. At the end of the file, point `[Unreleased]` at `compare/v<root version>...HEAD` and add a link for the new version comparing the previous tag. Pi shows a package's new changelog entries after an update and reads only `##` headings that start with a version, brackets allowed; it compares that version with the installed package's.
3. After the change merges, tag `main` as `v<root version>` and publish a GitHub release from that tag with the changelog section as its notes.
4. Pushing the tag publishes the pi package: `.github/workflows/publish-pi.yml` runs `npm publish` in `plugins/pi` through npm [trusted publishing](https://docs.npmjs.com/trusted-publishers) (OIDC), so no npm token or one-time code is involved. It fails when the tag is not `v<pi version>` and skips a version already on npm. To publish an existing tag again, run the workflow by hand: `gh workflow run publish-pi.yml -f tag=v<root version>`. npm trusts the workflow by its file name; the trusted publisher on npmjs.com (package settings, Trusted publishing) names `Dangerboi/kata-plugin` and `publish-pi.yml` and allows `npm publish`, so renaming the file stops publishing. `publishConfig` makes the scoped package public. Its `prepack` copies the root `LICENSE` and `CHANGELOG.md` into the package and `postpack` removes them again; `npm pack --dry-run` lists the files without publishing. The gallery preview, `pi.image` (and `pi.video`, if set), points at `docs/media/` on `main`, so a new preview shows once it is merged.
