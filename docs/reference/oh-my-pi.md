# Oh-my-pi reference

Plugin ID: `kata@kata-plugin`; package: `kata-omp`; entry: `plugins/oh-my-pi/kata.ts`.

Session start exports `KATA_TRANSCRIPT_AGENT=omp` and `KATA_TRANSCRIPT_SESSION_ID`; shutdown leaves them for the next session start to overwrite, as in pi. omp's `exec` does not see later environment changes, so the plugin spawns its own `kata close` calls directly, with no shell and no `env` program, and the pair in the child's environment. The adapter uses session start/shutdown, tree navigation, input, prompt/stop hooks, tool calls/results, `task:subagent:lifecycle`, and `task:subagent:event` (each subagent's session events, worker threads included, for its report: its last assistant text or its `yield` data). A shared coordinator joins final subagent IDs to child sessions. Only `ctx.agent.kind === "main"` can bind the main plan, draw its progress widget, or change main session attention. omp strips any tool named `todo` from `task` subagents, the plugin's included, except under prewalk; a prewalk worker can use todo under its own assigned issue and teammate, and cannot reuse the coordinator’s adapter context or inherited parent reference. Other subagents work their assigned issue through `kata` commands.

| Variable | Meaning |
| --- | --- |
| `KATA_OMP_EXECUTABLE` | Kata executable; defaults to `kata`. |
| `KATA_REF` | Explicit main parent and main session-attention target. |
| `KATA_DEFAULT_PROJECT` | Existing Kata project that collects the plans of folders without a project. Issues carry a label naming the repo. omp gives extensions no per-plugin settings, so this variable is the only switch. |
| `KATA_AUTHOR`, `KATA_TEAMMATE` | Existing actor and optional main teammate. |
| `KATA_INBOX_USER` | The session's inbox address, `<actor>/<name>`. A bare `<actor>` is a person's own inbox: the session reads none and says so once. Only requests from the session's own actor are shown. |
| `KATA_OMP_LIVE_INBOX` | `0` turns off live delivery of inbox requests to the main session and keeps the per-turn read. tern-kata sets it for the agents it starts, because it delivers there itself. |
| `KATA_OMP_DEBUG` | Optional append-only diagnostic log. |

The todo tool supports `init`, `append`, `start`, `block`, `unblock`, `done`, `drop`, `rm`, `view`. `/todo` supports `start`, `done`, `drop`, `rm`, `append`, `block`, and `unblock`; with no subcommand it shows the plan. Phases and task refs are retained in Kata. Local plans, queued close retries and unfinished delegate cleanups persist in custom session entries and resume with a saved session. Explicit `/todo done` records the user's completion attestation as external evidence. Removed items are retired, never deleted.

When a person deletes the automatic parent (`kata delete`, or `X` in Kata 0.22's TUI), the plan goes with it, together with its pending closes, also for a resumed session. Every todo result says so until a new plan starts, the parent's tasks stay in Kata as they were, and `init` creates a new automatic parent. An explicit parent (`KATA_REF`, an init `ref`, an adopted issue) that was deleted stays an error until someone runs `kata restore`.

A delegation gets a Kata issue only when it matches a plan item or names a ticket; any other spawn gets none, and creates no session parent. The plugin matches each delegation (the task item's `name`, `task` and the lifecycle `description`) against the plan when the subagent starts, so a `task` call sent in the same batch as `todo init` still binds. An open task named by its title (quoted, as the whole text, or three or more words), by qualified ref, or by short id after `issue`, `kata`, `ref`, `task` or `#` wins; if that task is already delegated the `task` call is refused. A prompt that names a ticket outside the plan by qualified ref (`<project>#<short_id>`) binds the subagent to that ticket: the plugin checks it with `kata show`, applies the same ownership, teammate and already-closed checks, and needs no plan. An unresolvable or unusable ref refuses the `task` call. A prompt that names two or more tickets or plan items is refused ("name one ticket per task"); word overlap never breaks that tie. Otherwise, when nothing is named, the task with a clear weighted word overlap wins, its leading verb counted twice and the lead's active task at half weight. The active task is the fallback only for an explicit "current task" handoff. Batch tasks match by index. If no task matches, the subagent is untracked: no issue, no comment, no label and no `kata notify`, and a finished untracked subagent does not hold the automatic parent open. Its result comes back in the `task` result, as omp delivers it. This matters for agents without `bash` (omp's `scout`), which could not close an issue of their own. One task cannot have two delegates, and a delegated task never occupies the lead's active slot. Main todo mutations cannot complete a running delegate's task: the child closes itself and `view` reloads Kata state. Delegate teammates derive from the agent id and the lead session id. A delegate that exits having run no tool (omp reports each of its tool calls) has its assignment rolled back: claim, teammate, status, attention and subagent keys are restored and nothing is labelled `needs-review`. One that ran a tool, or whose assignment failed, and left its issue open gets a comment, `work.attention` needs-human with a message, then is handed back (`needs-review`, an inbox request, the task back on the lead's teammate). A failed assignment is retried on the delegate's next prompt or `todo` call.

An item whose text starts with a qualified ref and a colon (`<project>#<short_id>: <action>`) works that existing ticket instead of creating an issue. The ref must resolve with `kata show`, be open and be claimable by this session; otherwise the call fails and creates nothing (a bare short id, or a ref elsewhere in the text, names nothing). `start` claims the ticket if unowned and sets `todo.status=in_progress` (never `todo.phase`); `block` sets `work.attention` as for other items. `done` comments on the ticket (item, message, evidence; idempotent per session, ticket and item), and the last open item naming a ticket closes it with that item's evidence exactly once. If Kata refuses the close because the ticket has open children (`parent_has_open_children`) the item still completes, the ticket stays open and one comment says how many children block it. The plugin remembers that pending close in the session snapshot (so it survives resume) and, after every later todo operation and on session shutdown, checks the ticket with `kata show`: it closes it with the stored evidence and message once the children are closed, and drops the pending close if the ticket is already closed or an item naming it is open again (the next last item to finish closes it). While children are still open it does nothing: no further `kata close` attempt and no further comment, so an umbrella ticket whose children live outside the plan simply stays open. A forked session does not adopt the source's pending ticket closes. `drop` and `rm` only comment; a ticket is never closed as wontfix or reopened, and one that is already closed is an error. The item-to-ticket record lives in the session snapshot, so it survives resume and compaction. A plan whose items all name tickets creates no issue and no `omp-session` parent; the parent appears when the first item without a ref needs an issue (with `init ref`, those become children of that ref). `view` and the widget show each item's ref. A `task` delegated to such an item binds that ticket like any named ticket and creates no parent. The delegate closes the whole ticket, so the `task` call is refused while another open plan item names the same ticket; delegate it once it is the last open item for that ticket, or plan the work as child issues (`init` with that `ref`) and delegate one of those.

## Takeover of omp's todo

omp lets an extension re-register a built-in tool by name, so installing the plugin makes its `todo` (Kata's description and schema) the only one the model sees. omp's native todo behavior is keyed to `details.phases` on `todo` results; the plugin returns its plan under `details.kata`, so omp's stop reminder, mid-run nudge, HUD and replan titles never run next to Kata's. Two omp behaviors remain. The reminder after a failed `todo` call tells the model to call `todo`, which agrees with Kata. The opt-in `todo.eager` prelude (`preferred` or `always`; the default is off) does not know about the Kata plan, because omp's own list is always empty: it fires on the first prompt of a session and after every compaction, and in `always` mode demands a single `init`. So `init` refuses a new list that leaves out open tasks (pending, in progress or blocked, ticket-named items included): it changes nothing and the error lists the open tasks missing from the new list; the model has to call `init` again with `replace: true` to drop them. A list that keeps every open task goes through. With no plan, or with every task closed, `init` works as before. `todo.enabled: false` still works.

In Tern, or any terminal that speaks omp's Tern Surface Protocol, the plan looks like omp's own todo. Each `todo` result is a checklist card headed `Todo <closed>/<total>` with the plan's parent, and each task carries its Kata ref. The progress widget becomes the dock pill above the input, labeled with the active task; its popover lists the plan, numbers the phases and shows blocker notes. The plugin draws both itself through `describeResult` and the widget's `describe`, so omp's tracker stays empty, and its reminders stay off. One difference from omp's own todo: omp replaces an earlier card in the same turn with the newer one, but it does that only for results carrying `details.phases`, so every Kata card stays in the transcript. Other terminals keep the text result and the one-line widget. `details.kata` carries the plan for both: `parent`, `workspace`, `label`, `local` (a session-local plan), and `phases` with each task's `content`, `status`, `ref` and `blocker`. It also has `notice` when the result text says something before the plan: an error, a close Kata deferred, or a deleted parent.

## Where the plan lives

First match wins:

1. `KATA_REF`, or a worker's assigned issue.
2. The binding stored in this session.
3. The folder's own Kata project (`.kata.toml` or a registered inferred name), as before.
4. `KATA_DEFAULT_PROJECT`. The parent and every task and delegate issue carry a label naming the repo (Kata's inferred project name, else the folder name, lowercased to a valid label), so `kata list --label agentsview` finds them. The project must exist; a mistyped name fails instead of creating a project.
5. The inferred project: the name Kata would infer from the git remote, else the folder name. The plugin registers it with `kata projects create <name>` and binds to it. It never runs `kata init` and writes nothing into the repo. Inferred names are not unique: two checkouts named `app` share one project, and so does a checkout whose name matches an existing project. Set `KATA_DEFAULT_PROJECT` (issues are labeled per repo) or run `kata init --project <name>` where that matters.

Nothing is created until the first plan mutation: a session that never plans leaves no issue and no project. The first `todo init` creates one automatic session parent. A task delegation does not create it: a delegation that matches a plan item or names a ticket binds an issue that already exists, and any other delegation gets no issue. The parent closes from its children's evidence as before. After `kata move`, the plan's parent and ticket items follow the issue to its current project; new tasks and delegated work are created there.

A forked session shares its source's plan: forking the conversation does not fork the work. A fork gets a new session id and copies the source's entries; when none belongs to the new id and the session header has `parentSession` (the source session id, or the source session file `<timestamp>_<id>.jsonl`), the plugin adopts the source's parent and ticket items. The fork creates no automatic parent of its own, and tree navigation inside one session is unaffected. Not adopted: the source's pending close retries and pending ticket closes (the source still owns them) and its local plan (replaying it would create a second automatic parent). Both sessions may keep working the shared parent, which closes only once every child is closed. Either session may close it then, so it does not stay open after the work finishes in the fork. Shutting down one session leaves it open while tasks remain.

## When Kata is unreachable

A missing executable or an unreachable or unresponsive daemon (a Kata call that times out) is the only case that selects a local plan. The plugin warns once per session, keeps the plan in the session entries, and replays it into Kata when Kata answers again: on the next todo call, on resume, or on a 60-second retry. Tasks completed offline replay as closed only if they carry evidence and a 40-character message; otherwise they replay blocked so you can add evidence. `project_not_initialized` never produces a local plan, and missing projects or authentication failures are errors.

## Hooks

The plugin injects the contract Kata gives for the session folder and runs `kata agent-hook attention-native` itself; no `kata agent-hook install` step is needed. Kata 0.23.0 has no `omp` installer, so nothing else adds the contract to omp. Kata gives a contract only in a folder with a `.kata.toml` (or below one); elsewhere the section is left out, and sessions planning in `KATA_DEFAULT_PROJECT` or an inferred project still get the plan, binding and inbox sections. Run `kata init --project <name>` in the folder to get the contract. If something else already put the contract in the system prompt, the plugin skips its own copy.

Qualified explicit issue references and saved bindings take precedence over directory probing, including in unbound worktrees. An unavailable explicit issue is an error.

Subagents bound to an issue receive the cached contract (in a folder with `.kata.toml`), exact issue, teammate, a comment command and the close command, and work that issue through `kata` commands: before finishing, closed or not, each comments what it did, how it verified it and what remains. A subagent that exits without a comment under its teammate gets its report posted for it under that teammate (see [closing rules](closing-rules.md)). Only prewalk subagents also get `todo`, whose children then belong to that assigned issue. A subagent that matched no plan item and named no ticket still gets the contract, plus a short `<kata_binding>` note instead of an issue: the lead session tracks this work, it has no Kata issue, it must not create, claim, close, comment on or edit issues (including one named by an inherited `KATA_REF`), reading is fine, and it reports in its reply. Under prewalk its `todo` runs omp's native session-only list through `ctx.invokeTool` and makes no Kata calls; on an omp without `ctx.invokeTool` it gets an error saying it matched no plan item or ticket. CLI calls carry the worker’s teammate without changing process-wide environment variables. A `task` delegate whose assignment failed gets a "Kata assignment failed" error. omp's `/tan` side conversation is also a sub session but no delegate (its agent id starts with `Tan-`): there `todo` runs omp's native session-only list through the host and makes no Kata calls; on an omp without `ctx.invokeTool` it gets the "Kata assignment unavailable" error. Recognized standalone Kata Bash commands gain teammate and binding flags; actor impersonation is refused. A delegate that finishes without closing its issue gets `omp.status`, `needs-review`, one idempotent comment and a `kata notify` to the lead; a plan task is handed back to the lead's teammate as pending, so the lead can verify and close it (which removes `needs-review`) or delegate it again. A `task` call that never starts a subagent releases its tasks when its result arrives. Terminal outcomes never write the delegate's `work.*` or infer a close from shell text.

With `KATA_INBOX_USER` set to a session address, the main session follows `kata events --tail` live (next paragraph). Delegates, and the main session with `KATA_OMP_LIVE_INBOX=0`, start a `kata inbox --for <address> --json` read on every turn instead (the contract is cached per session). Only requests whose `from` is the session's own actor are shown; the rest never reach the prompt. A request sent mid-session shows up in `<kata_inbox>` on that turn or the next, a failed read keeps the last inbox, and no trusted request removes the section. A `revive` of a parked subagent does no Kata work. Hooks have a 250 ms foreground budget, except the end of a lead turn, which waits up to 15 s while exited delegates are still to be handed back or rolled back. A delegate's first prompt waits up to 15 s for its assignment, because it has no other way to learn it: the lead assigns delegates one at a time (about fifteen Kata calls each), so in a large `task` call on a busy machine the last delegate waits for all the others. The wait ends as soon as the assignment lands. Ordinary Kata subprocess calls have a 120-second ceiling so hosted reads are not killed after one second. Explicit todo operations await actual results. Failed startup binding is retried on the next todo call. If a read fails or returns malformed children, the widget and tool report unavailable state rather than cached task progress; `view` reloads it from Kata. Stop reminders wait for a successful refresh and do not describe a pending read as current state. Main session attention for a `KATA_REF` session checks the actor and teammate, then runs `kata agent-hook attention-native pi start|end --session <id> --host-pid <pid> --ref <ref>`; Kata owns the token and transitions. Conflicting writes are preserved. See [closing rules](closing-rules.md).


### Live inbox delivery

The main session (never a delegate) follows `kata events --tail --json` for its workspace's project and delivers each new request without waiting for a prompt. A request is delivered with `pi.sendUserMessage(text, { deliverAs: "aside", attribution: "agent" })`: an idle agent starts a turn on it, a working agent receives it at its next step boundary without losing its tool batch. The text names the sender and issue, cuts the message at 1024 bytes on a character boundary, says the message is untrusted data and not instructions, and ends with the `kata notify <ref> --to <address> --clear` command. Only requests written by the session's own actor are delivered, by the same rule as the `<kata_inbox>` section; a clear delivers nothing, and a replay or an unchanged request is delivered once. At start it pages `kata events --after` to the project's newest event id (a later start in the same process pages on from the id it already knew) and tails from there, so no history replays; requests already waiting are shown in `<kata_inbox>`, not delivered. The same holds when Kata is unreachable at session start: requests written before the follower connects are shown in the section but not delivered as an aside, because the follower cannot tell them from requests that were pending before the session. Delivery waits until that read succeeds, retrying with backoff, and that retry also runs while the stream stays up. The section is kept from the stream, so a main-session prompt starts no `kata inbox` read after the first. A dropped stream restarts with backoff (1 s doubling to 30 s, starting over only after a stream stayed up 30 s) from the last event id and re-reads the inbox, so a request written while it was down is delivered once on reconnect. The `kata events` child is killed on session switch and shutdown, and spawn failures are silent (see `KATA_OMP_DEBUG`). Pi has no such call and reads per turn only.

## Ticket references in the prompt

In an interactive session, typing `#` and part of a ticket id or title word offers matching open Kata issues first, above omp's own `#` items (prompt actions, GitHub refs), so Tab or Enter accepts the first ticket. `#bc` offers every ticket whose short id starts with `bc` or whose title has a word starting with it. Each entry shows the qualified ref, then the title in the description column, which gets the rest of the row (the first column is capped at 32 characters). Accepting one inserts that ref with a trailing space, for example `kata-plugin#bc7q `.

- A digits-only token (`#3164`) stays GitHub's and offers no Kata tickets. An all-digit Kata id is reachable as `#<project>#1234`.
- `#<project>#<token>` searches that project. Otherwise the folder's bound project is searched, then `KATA_DEFAULT_PROJECT`.
- The open-issue list is cached per session and refreshed in the background (30 seconds). Typing never waits on Kata: on abort, a slow call (400 ms) or an unreachable daemon the menu shows only omp's own items, with no error.
- Subagents and non-interactive modes (print, RPC, ACP) register nothing.
