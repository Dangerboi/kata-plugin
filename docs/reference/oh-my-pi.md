# Oh-my-pi reference

Plugin ID: `kata@kata-plugin`; package: `@dangerboi/kata-omp` (marketplace and npm); entry: `plugins/oh-my-pi/kata.ts`. Requires oh-my-pi 19.1.1 or later (for `registerTodoBackend`) and Kata 0.23.0 or later, checked before CLI use; see [runtime compatibility](../how-to/install.md#runtime-compatibility) for errors, source builds and background hook behavior.

Session start exports `KATA_CLOSE_TRANSCRIPT_ENABLED=true` (unless already set), `KATA_TRANSCRIPT_AGENT=omp` and `KATA_TRANSCRIPT_SESSION_ID`; shutdown leaves them for the next session start to overwrite, as in pi. omp's `exec` does not see later environment changes, so the plugin spawns its own `kata close` calls directly, with no shell and no `env` program, and the pair in the child's environment. The adapter uses a todo backend, session start/shutdown, tree navigation, input, prompt hooks, tool calls/results, the stop hook (`session_stop`: it settles the turn, retrying due closes and handing back exited delegates, and adds no reminder, because omp's own todo tracker reminds), `task:subagent:lifecycle`, and `task:subagent:event` (each subagent's session events, worker threads included, for its report: its last assistant text or its `yield` data). A shared coordinator joins final subagent IDs to child sessions. Only `ctx.agent.kind === "main"` can bind the main plan or change main session attention. omp strips its `todo` tool from `task` subagents except under prewalk; a prewalk worker with an assignment has its `todo` calls checked against its own assigned issue and teammate, and cannot reuse the coordinator’s adapter context or inherited parent reference. Other subagents work their assigned issue through `kata` commands.

| Variable | Meaning |
| --- | --- |
| `KATA_OMP_EXECUTABLE` | Kata executable; defaults to `kata`. |
| `KATA_REF` | Explicit main parent and main session-attention target. |
| `KATA_DEFAULT_PROJECT` | Existing Kata project that collects the plans of folders without a project. Issues carry a label naming the repo. omp gives extensions no per-plugin settings, so this variable is the only switch. |
| `KATA_AUTHOR`, `KATA_TEAMMATE` | Existing actor and optional main teammate. |
| `KATA_INBOX_USER` | The session's inbox address, `<actor>/<name>`. A bare `<actor>` is a personal inbox: the session reads none and says so once. Only requests from the session's own actor are shown. |
| `KATA_OMP_LIVE_INBOX` | `0` turns off live delivery of inbox requests to the main session and keeps the per-turn read. tern-kata sets it for the agents it starts, because it delivers there itself. |
| `KATA_CLOSE_TRANSCRIPT_ENABLED` | `false` in the environment that launches omp stops closes recording the session; unset, session start sets `true`. |
| `KATA_REF_GUARD` | `off` or `0` stops the refusal of writes and commits that name a Kata ref ([below](#kata-refs-in-repository-content)). On by default. |
| `KATA_OMP_DEBUG` | Optional append-only diagnostic log. |

## omp's todo and the Kata backend

The plugin does not replace omp's `todo`. omp's own tool, `/todo`, HUD, reminders and nudges run as they do without the plugin, and omp draws the list (in Tern too); the plugin draws nothing of its own. It registers a todo backend named `kata` (`pi.registerTodoBackend`) and checks `todo` calls in `tool_call`.

Select the backend under `/settings` → Tools → Todos → Todo Backend, or set `todo.backend: kata` in omp's config. The plugin never sets it. Until Kata is selected, todos are omp's own: nothing reaches Kata, no call is refused, and the main session shows one notice per session naming the setting.

**Mirror.** After omp saves each change to its list, the backend gets the whole list and applies what changed. The first list with open tasks starts the plan; a new task creates a child issue of the plan parent; `in_progress` claims and starts it; back to `pending` pauses it; a task dropped (`abandoned`) or removed from the list closes as wontfix. Removed items are retired, never deleted.

- Tasks are matched by their text, which omp keeps unique across phases. Moving a task to another phase in omp is not mirrored.
- Changes made in Kata stand: an agent's `kata close`, a delegate's close, a hand back. The mirror does not undo them.
- A task that was never in omp's list (an open child of an adopted parent, of `KATA_REF` or of a claimed ticket) is never removed by the mirror.
- A task marked completed in omp's list while its issue is still open (the user's `/todo`, or RPC `set_todos`) stays open, labeled `needs-review` with one comment saying why.
- A change Kata cannot take leaves omp's list as it is: the plugin warns once, and the next change sends the whole list again.

**Guard.** Before omp runs an `init`, `start`, `done`, `drop` or `rm`, the plugin reads Kata and refuses a call Kata's rules forbid; the model gets the reason as the tool's error.

- `done` on a task whose issue is still open is refused. The reason names the issue's ref and the command: `kata close <ref> --done --message '<40+ characters>' --test '<command>'` (or `--commit`, `--pr`, `--reviewed-paths`). The agent closes the issue in its shell, then calls `done` again, so the evidence and message go on Kata's close, not on `todo`.
- `done` on a delegated task is refused: its delegate closes it.
- `init` whose list leaves out open tasks is refused and lists them, also an empty list (`list: []`) and an `init` with `op` left out. For tasks omp's list held, drop them first (`todo drop`, which closes them as wontfix) in an earlier call, then `init`. For tasks omp never held (an open child of an adopted parent, of `KATA_REF` or of a claimed ticket), keep them in the list, or `append` them and then drop them.
- Any op on a task another lead session holds is refused, telling the model to ask the user, who runs `/todo takeover <task>` (see [closing rules](closing-rules.md)).

The guard waits up to 10 seconds for Kata; past that, or while the plan is local, the call goes through unchecked. User `/todo` edits and RPC `set_todos` do not pass through `tool_call`, so they are mirrored, never refused.

`/todo takeover <task>` and `/todo ref <ref>` are the only `/todo` subcommands the plugin handles; omp handles every other `/todo`. `takeover` starts the task in this session, taking it over from the session that holds it, with a comment on the issue naming both. `ref` makes the issue the plan parent at once and loads its open children; naming the current automatic parent makes it explicit, so it no longer closes itself. A plan that already has another parent keeps it, and with `KATA_REF` set the ref is not used.

omp has had no `blocked` status since 18.20.0, so there is no `block` or `unblock` on omp: record a wait with `kata comment`. omp's own stop reminder still fires while tasks are open. The plan section of the system prompt states these rules and lists the plan with each task's ref. Local plans, queued close retries and unfinished delegate cleanups persist in custom session entries and resume with a saved session.

When a person deletes the automatic parent (`kata delete`, or `X` in Kata 0.22's TUI), the plan goes with it, together with its pending closes, also for a resumed session. The parent's tasks stay in Kata as they were, and the next list omp saves starts a new automatic parent. An explicit parent (`KATA_REF`, `/todo ref`, a claimed or adopted issue) that was deleted stays an error until someone runs `kata restore`.

## Kata refs in repository content

Kata refs resolve only in the local tracker, so the plugin refuses a `write`, `edit` (hashline, replace and `apply_patch` text), `ast_edit` replacement or `bash` call that puts a ref the session works (the plan parent and items, the assigned or claimed issue, a delegate's issue) into a file under the session's folder or into a `git commit` message, and the model rewrites it to describe the behaviour. A qualified ref counts only when its project is one the session knows, so `README.md#tasks` passes. A bare short id counts only when the session knows it. Only added text is checked: removed and context lines, hashline headers, files outside the folder, internal URLs and the bodies of `kata comment`, `kata close` and `kata create` are not. The check waits at most 2 seconds and lets the call through on an error. `KATA_REF_GUARD=off` (or `0`) turns it off. The lead's and every delegate's `tool_call` is checked against the lead's refs, so a delegate cannot write the ref of its own issue either; a delegate in a worker thread knows only its own assignment. The refusal is the tool's error.

## Delegates

A delegation gets a Kata issue to work only when it names a plan item or a ticket; any other spawn runs untracked, and its run is recorded as a mission once it exits (below). Nothing is guessed from the spawn's words: a spawn that only describes an item's work runs untracked, and the lead finishes that item itself. The plugin reads each delegation (the task item's `name`, `task` and the lifecycle `description`) against the plan when the subagent starts, so a `task` call sent in the same batch as `todo init` still binds. An open task is named by its title (quoted, as the whole text, or three or more words), by qualified ref, by short id after `issue`, `kata`, `ref`, `task` or `#`, or, for a ticket item, by its ticket's qualified ref; if that task is already delegated the `task` call is refused. The plan parent's own ref names nothing, so a brief may cite it. A prompt that names a ticket outside the plan by qualified ref (`<project>#<short_id>`) binds the subagent to that ticket: the plugin checks it with `kata show`, applies the same ownership, teammate and already-closed checks, and needs no plan. An unresolvable ref, or a ticket the assignment rules refuse, refuses the `task` call; a Kata that cannot be reached refuses nothing: the spawn runs and its assignment is retried on the delegate's next use. A prompt that names two or more tickets or plan items is refused ("name one ticket per task"). Batch tasks match by index. If no task is named, the subagent is untracked: it works no issue, gets no label and no `kata notify`, and its result comes back in the `task` result, as omp delivers it. When it exits with a report, the plugin records its run as a mission: a child of the plan parent titled `Subagent <name>: <first line of its task>`, with the task text as its body, `omp.mission` `true`, `omp.mission_subagent_id` (its id) and `omp.mission_agent` (omp's agent name, such as `scout`), and its report as a comment under its teammate. A plan with no parent gets its automatic parent for the mission; none is made beside an explicit parent. The plugin closes the mission at once as `audit-no-change`: a report proves no change, and any change the run made is the lead's to verify. The subagent writes nothing to Kata itself, so agents without `bash` (omp's `scout`) get a mission too. An untracked subagent that exits with no report leaves nothing, and a finished one does not hold the automatic parent open; a mission adds no evidence to its close (see [closing rules](closing-rules.md)). One task cannot have two delegates, and a delegated task never occupies the lead's active slot. The lead's `todo done` on a delegated task is refused: the delegate closes it. A delegate is told to close its issue once its work is verified, unless its task text says not to close issues or to leave the issue open; it then exits with the issue open and is handed back as below, so the lead closes it after its own checks. Delegate teammates derive from the agent id and the lead session id. A delegate that exits having run no tool (omp reports each of its tool calls) has its assignment rolled back: claim, teammate, status, attention and subagent keys are restored and nothing is labelled `needs-review`. One that ran a tool, or whose assignment failed, and left its issue open gets a comment, `work.attention` needs-human with a message, then is handed back (`needs-review`, an inbox request, the task back on the lead's teammate). A failed assignment is retried on the delegate's next prompt or `todo` call.

What a `task` call's spawns named stays reserved until each subagent starts or the call is over: at its result, or for a background call once its jobs stop running. A background subagent that starts after the call returned therefore still gets the plan item or ticket its spawn named, and a second call naming it meanwhile is refused. omp reports every later turn of the same subagent (a revival, or its answer to a message) as a new start; the plugin keeps it on its record. A subagent that had an issue reports on that issue again: an open one is assigned to it again, a closed one is never reopened, and its report is posted as a comment marked `after a follow-up`. An untracked subagent's later report goes on the mission its first run made. A subagent whose earlier run left nothing in Kata starts over.

## Ticket items

An item whose text starts with a qualified ref and a colon (`<project>#<short_id>: <action>`) works that existing ticket instead of creating an issue. The ref must resolve with `kata show`, be open and be claimable by this session; otherwise the mirror creates nothing for it, and omp's list keeps the item (a bare short id, or a ref elsewhere in the text, names nothing). `start` claims the ticket if unowned and sets `todo.status=in_progress` (never `todo.phase`). `done` on an item that is not the ticket's last open item goes through, and the mirror comments on the ticket (idempotent per session, ticket and item). `done` on the ticket's last open item is refused until the ticket is closed: the agent runs `kata close` on the ticket, then calls `done` again. The plugin never closes a ticket itself. An item the user marks completed through `/todo` while its ticket is open gets a comment on the ticket, and the ticket is labeled `needs-review` when that was its last open item. `drop` and `rm` only comment; a ticket is never closed as wontfix or reopened. The item-to-ticket record lives in the session snapshot, so it survives resume and compaction. A plan whose items all name tickets creates no issue and no `omp-session` parent; the parent appears when the first item without a ref needs an issue (under an explicit parent, those become its children), or when an untracked subagent leaves a mission. The plan section of the system prompt shows each item's ref. A `task` delegated to such an item binds that ticket like any named ticket and creates no parent. The delegate closes the whole ticket, so the `task` call is refused while another open plan item names the same ticket; delegate it once it is the last open item for that ticket, or make the ticket the plan parent (`kata claim <ref>` or `/todo ref <ref>`), plan the work as its children and delegate one of those.

## Where the plan lives

First match wins:

1. `KATA_REF`, or a worker's assigned issue.
2. The binding stored in this session: a ticket the session claimed (`kata claim <ref>`, run on its own as a `bash` command), an issue named with `/todo ref <ref>`, or the parent the session already has.
3. The folder's own Kata project (`.kata.toml` or a registered inferred name), as before.
4. `KATA_DEFAULT_PROJECT`. The parent and every task and delegate issue carry a label naming the repo (Kata's inferred project name, else the folder name, lowercased to a valid label), so `kata list --label agentsview` finds them. The project must exist; a mistyped name fails instead of creating a project.
5. The inferred project: the name Kata would infer from the git remote, else the folder name. The plugin registers it with `kata projects create <name>` and binds to it. It never runs `kata init` and writes nothing into the repo. Inferred names are not unique: two checkouts named `app` share one project, and so does a checkout whose name matches an existing project. Set `KATA_DEFAULT_PROJECT` (issues are labeled per repo) or run `kata init --project <name>` where that matters.

Nothing is created until the first plan change or the first mission: a session that never plans and runs no untracked subagent leaves no issue and no project. The first list omp saves with open tasks creates one automatic session parent when none of the sources above names one. A task delegation does not create it when it starts: a delegation that names a plan item or a ticket binds an issue that already exists, and any other delegation works no issue. An untracked subagent that exits with a report creates the automatic parent when the plan has none, to hold its mission. The parent closes from its children's evidence as before. After `kata move`, the plan's parent and ticket items follow the issue to its current project; new tasks and delegated work are created there.

A forked session shares its source's plan: forking the conversation does not fork the work. A fork gets a new session id and copies the source's entries; when none belongs to the new id and the session header has `parentSession` (the source session id, or the source session file `<timestamp>_<id>.jsonl`), the plugin adopts the source's parent and ticket items. The fork creates no automatic parent of its own, and tree navigation inside one session is unaffected. Not adopted: the source's pending close retries and pending ticket closes (the source still owns them) and its local plan (replaying it would create a second automatic parent). Both sessions may keep working the shared parent, which closes only once every child is closed. Either session may close it then, so it does not stay open after the work finishes in the fork. Shutting down one session leaves it open while tasks remain.

## When Kata is unreachable

A missing executable or an unreachable or unresponsive daemon (a Kata call that times out) is the only case that selects a local plan. omp's list is never held up by Kata: the plugin warns once, keeps the plan in the session entries, refuses no `todo` call meanwhile, and replays the plan into Kata when Kata answers again: on the next change to the list, on resume, or on a 60-second retry. A task marked completed while the plan was local has no Kata close, so it replays open, waiting for evidence; close it with `kata close` once Kata is back. `project_not_initialized` never produces a local plan, and missing projects or authentication failures are errors.

## Hooks

The plugin injects the contract Kata gives for the session folder and runs `kata agent-hook attention-native` itself; no `kata agent-hook install` step is needed. Kata 0.23.0 has no `omp` installer, so nothing else adds the contract to omp. Kata gives a contract only in a folder with a `.kata.toml` (or below one); elsewhere the contract section is left out. The inbox section needs the folder to resolve to a Kata project: it works through a `.kata.toml`, or a git remote that `kata init` linked to a project in another clone. A session that plans in `KATA_DEFAULT_PROJECT`, or in the inferred project the plugin registers, gets the plan and assignment sections but no inbox. Run `kata init --project <name>` in the folder to get the contract; this also moves the folder's new plans from `KATA_DEFAULT_PROJECT` to that project. If something else already put the contract in the system prompt, the plugin skips its own copy.

Qualified explicit issue references and saved bindings take precedence over directory probing, including in unbound worktrees. An unavailable explicit issue is an error.

Subagents bound to an issue receive the cached contract (in a folder with `.kata.toml`), exact issue, teammate, a comment command and the close command, and work that issue through `kata` commands: before finishing, closed or not, each comments what it did, how it verified it and what remains. A subagent that exits without a comment under its teammate gets its report posted for it under that teammate (see [closing rules](closing-rules.md)). Only prewalk subagents also get omp's `todo`; the plugin checks their calls by the same rules as the lead's. A subagent that matched no plan item and named no ticket still gets the contract (in a folder with `.kata.toml`; elsewhere Kata gives an empty contract and no section is added), plus a short `<kata_binding>` note instead of an issue: the lead session tracks this work, it has no Kata issue, it must not create, claim, close, comment on or edit issues (including one named by an inherited `KATA_REF`), reading is fine, and it reports in its reply. Under prewalk its `todo` is omp's own session list and makes no Kata calls, as is the `todo` of omp's `/tan` side conversation. CLI calls carry the worker’s teammate without changing process-wide environment variables. A `task` delegate whose assignment failed gets a "Kata assignment failed" error. Recognized standalone Kata Bash commands gain teammate and binding flags; actor impersonation is refused. A delegate that finishes without closing its issue gets `omp.status`, `needs-review`, one idempotent comment and a `kata notify` to the lead; a plan task is handed back to the lead's teammate as pending, so the lead can verify and close it (which removes `needs-review`) or delegate it again. A delegate that closed its issue leaves it closed; once it exits, the plugin returns it to the lead: the lead's teammate (while the issue still carries the delegate's), `omp.status` set to the delegate's outcome, `todo.status` completed (abandoned when closed as wontfix) and `omp.subagent_id` removed, so the lead can still retire the item from a new plan. An exiting delegate never hands back or returns an issue that another delegate's subagent id, or the same id under another lead session, marks, so a forked session's delegate of the same name leaves the source delegate's issue alone, open or closed. A closed item still marked by a delegate that no unfinished delegate of the session holds (left by an earlier version, a lead that was never resumed, or another session) is returned to the lead the same way when a plan operation touches it, as long as the lead's actor owns it, with `omp.status` `ended` in place of `running`; `start` or appending it again then reopens it. An open item held by a delegate is still refused. A `task` call that never starts a subagent releases its tasks when its result arrives. Terminal outcomes never write the delegate's `work.*` or infer a close from shell text.

With `KATA_INBOX_USER` set to a session address, the main session follows `kata events --tail` live (next paragraph). Delegates, and the main session with `KATA_OMP_LIVE_INBOX=0`, start a `kata inbox --for <address> --json` read on every turn instead (the contract is cached once Kata gives a non-empty one). Only requests whose `from` is the session's own actor are shown; the rest never reach the prompt. A request sent before a turn shows up in `<kata_inbox>` on that turn, also when an earlier read was still answering (on the next one only when the read outlasts the turn's budget), a failed read keeps the last inbox, and no trusted request removes the section. A `revive` of a parked subagent does no Kata work. Hooks have a 250 ms foreground budget, except main session start or switch with `KATA_REF`, which waits up to 10 s for the plan binding, attention and its host marker, and the end of a lead turn, which waits up to 15 s while exited delegates are still to be handed back or rolled back. A delegate's first prompt waits up to 15 s for its assignment, because it has no other way to learn it: the lead assigns delegates one at a time (about fifteen Kata calls each), so in a large `task` call on a busy machine the last delegate waits for all the others. The wait ends as soon as the assignment lands. Ordinary Kata subprocess calls have a 120-second ceiling so hosted reads are not killed after one second. The `todo` guard waits up to 10 s, then lets the call through unchecked; the mirror runs after omp has saved its list and never holds it up. Failed startup binding is retried on the next change to the list. If a read fails or returns malformed children, the plan section reports unavailable state rather than cached task progress. Main session attention for a `KATA_REF` session checks the actor and teammate, then runs `kata agent-hook attention-native pi start|end --session <id> --host-pid <pid> --ref <ref>`; Kata owns the token and transitions. With `KATA_REF`, the omp lead publishes Kata’s `KATA_ATTENTION_HOST` before session start or switch returns, so native Pi children it starts from bash with the same ref, folder and daemon leave its attention token unchanged. omp refreshes the environment its bash tool passes on when those handlers return, so a start that takes longer than 10 s publishes the marker too late for bash until the next switch or branch, and children started meanwhile track the issue themselves as before. Conflicting writes are preserved. See [closing rules](closing-rules.md).


### Live inbox delivery

The main session (never a delegate) follows `kata events --tail --json` for its workspace's project and delivers each new request without waiting for a prompt. A request is delivered with `pi.sendUserMessage(text, { deliverAs: "aside", attribution: "agent" })`: an idle agent starts a turn on it, a working agent receives it at its next step boundary without losing its tool batch. The text names the sender and issue, cuts the message at 1024 bytes on a character boundary, says the message is untrusted data and not instructions, and ends with the `kata notify <ref> --to <address> --clear` command. Only requests written by the session's own actor are delivered, by the same rule as the `<kata_inbox>` section; a clear delivers nothing, and a replay or an unchanged request is delivered once. At start it pages `kata events --after` to the project's newest event id (a later start in the same process pages on from the id it already knew) and tails from there, so no history replays; requests already waiting are shown in `<kata_inbox>`, not delivered. The same holds when Kata is unreachable at session start: requests written before the follower connects are shown in the section but not delivered as an aside, because the follower cannot tell them from requests that were pending before the session. Delivery waits until that read succeeds, retrying with backoff, and that retry also runs while the stream stays up. The section is kept from the stream, so a main-session prompt starts no `kata inbox` read after the first. A dropped stream restarts with backoff (1 s doubling to 30 s, starting over only after a stream stayed up 30 s) from the last event id and re-reads the inbox, so a request written while it was down is delivered once on reconnect. The `kata events` child is killed on session switch and shutdown, and spawn failures are silent (see `KATA_OMP_DEBUG`). Pi has no such call and reads per turn only.

## Ticket references in the prompt

In an interactive session, typing `#` and part of a ticket id or title word offers matching open Kata issues first, above omp's own `#` items (prompt actions, GitHub refs), so Tab or Enter accepts the first ticket. `#bc` offers every ticket whose short id starts with `bc` or whose title has a word starting with it. Each entry shows the qualified ref, then the title in the description column, which gets the rest of the row (the first column is capped at 32 characters). Accepting one inserts that ref with a trailing space, for example `kata-plugin#bc7q `.

- A digits-only token (`#3164`) stays GitHub's and offers no Kata tickets. An all-digit Kata id is reachable as `#<project>#1234`.
- `#<project>#<token>` searches that project. Otherwise the folder's bound project is searched, then `KATA_DEFAULT_PROJECT`.
- The open-issue list is cached per session and refreshed in the background (30 seconds). Typing never waits on Kata: on abort, a slow call (400 ms) or an unreachable daemon the menu shows only omp's own items, with no error.
- Subagents and non-interactive modes (print, RPC, ACP) register nothing.
