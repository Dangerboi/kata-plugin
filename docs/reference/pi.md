# Pi reference

Package: `@dangerboi/kata-pi` on npm; portable entry: `plugins/pi/kata.ts`. The repository root has a `pi.extensions` shim for Git installation. Pi supplies TypeBox and its extension API through declared peers. The entry exits under OMP before loading TypeBox. Requires Kata 0.23.0 or later, checked before CLI use; see [runtime compatibility](../how-to/install.md#runtime-compatibility) for errors, source builds and background hook behavior.

| Event/surface | Behavior |
| --- | --- |
| `session_start` | Restore saved plans/retries or child binding; a child clears the inherited lead `KATA_REF`. Export the child-process marker, plus `KATA_CLOSE_TRANSCRIPT_ENABLED=true` (unless already set), `KATA_TRANSCRIPT_AGENT=pi` and `KATA_TRANSCRIPT_SESSION_ID`; a child replaces the pair it inherited. |
| `session_tree`, `session_shutdown` | Reload/drain reconciliation; a child that exits with its issue open restores it (no tool run) or hands it back for review. A child's shutdown passes the text of its last assistant message that has any as its report, posted when it left no comment of its own. `session_shutdown` leaves the transcript variables alone: a reload or new session starts the next instance in the same process, and that instance's `session_start` overwrites the pair. Clearing at shutdown could delete the new pair after a slow cleanup. |
| `before_agent_start` | Bind inherited child work, inject its contract and exact issue/teammate/comment and close commands, or add the main plan and fallback context. |
| `agent_before_settle` | Add a hidden continuation for actionable unfinished main work, within a three-reminder progress budget. Questions, blockers, aborts and errors suppress it. |
| `tool_call` | Ensure a parent before a Bash command that launches `pi`; mutate Bash input in place to route bare `kata` and enforce child teammate attribution. Refuse child `--as`. |
| `tool_result` | Observe successful standalone main claims; ignore failed results. |
| `registerCommand("todo")`, `input` | Provide `/todo` and visible command replies. |

Before a `write`, an `edit` (`edits[].newText`, or a top-level `newText`) or a `bash` call runs, `tool_call` refuses it when it would put a Kata ref into the repository. Kata refs resolve only in the local tracker, so the plugin refuses a call that adds a ref the session works (the plan parent and items, the assigned or claimed issue) to a file under the session's folder or to a `git commit` message, and the model rewrites it to describe the behaviour. A qualified ref counts only when its project is one the session knows, so `README.md#tasks` passes; a bare short id counts only when the session knows it. Only added text is checked: refs the replaced text or the file already holds, removed and context lines, files outside the folder, internal URLs and the bodies of `kata comment`, `kata close` and `kata create` are not. A delegate running as a child process checks against its own assignment and parent. The check waits at most 2 seconds and lets the call through on an error. `KATA_REF_GUARD=off` (or `0`) turns it off.

`KATA_PI_EXECUTABLE` selects the executable, falling back to `KATA_OMP_EXECUTABLE`, then `kata`. Debug output uses `KATA_PI_DEBUG`, with `KATA_OMP_DEBUG` as fallback. Existing actor identity is preserved. Explicit executable paths and quoted data are not rewritten.

Main sessions export `KATA_PI_PARENT` with their process/session identity, qualified parent ref, workspace, and teammate seed. After `kata move`, a child started with the old ref re-pins it. A child Pi process inherits that marker, retains the actor, derives a distinct teammate, and sets its own inbox recipient, which its assignment or `<kata_binding>` note names (`Your Kata inbox is <actor>/<teammate>`). On pi 1.2 and later, a child whose first run starts from a custom message (`pi.sendMessage` with `triggerTurn`) is matched by that message's text instead of a prompt. A child prompt is matched against every open child of the parent with the same rules as OMP: it binds only the child it names by title (quoted, as the whole prompt, or three or more words), qualified ref or short id, and nothing is guessed from its words; a prompt that names two tickets or plan items, or names none, or whose named task is already delegated or owned by another writer, is an untracked delegate: it creates no issue to work, gets the untracked context (it has no Kata issue and must not create, claim or close issues; reading is fine) and its `kata` calls are still rewritten with its teammate. What its run leaves once it exits with a report depends on why it is untracked. A child that named nothing gets a mission under the lead's parent, as an [untracked omp subagent](oh-my-pi.md) does (`pi.mission`, `pi.mission_subagent_id` with its session id, no agent name). A child that named two or more tickets or plan items gets its report posted as a comment on each of them, under its teammate, and none of them is closed. A child whose named task was already delegated, held or not delegable records nothing. An assigned child works its issue through the shared delegate lifecycle: claim through the ownership checks, its teammate, `pi.subagent_id`, `pi.session_id`, `todo.status` in progress and `work.attention` ok; its own `todo` plans under that issue. Its binding tells it to comment on the issue what it did, how it verified it and what remains before it finishes, closed or not; a child that exits without a comment under its teammate gets the text of its last assistant message that has any posted as its report (see [closing rules](closing-rules.md)). Its assignment also tells it to close the issue once its work is verified, unless its task text says not to close issues or to leave the issue open; it then exits with the issue open and is handed back as below. A child that exits having run no tool restores the issue (claim, teammate, status, attention and subagent key, no `needs-review`); one that ran a tool and left the issue open comments, sets `work.attention` to needs-human and hands it back (`needs-review`, an inbox request, the task back on the lead's teammate). One that closed its issue leaves it closed; once it exits, the plugin returns it to the lead: the lead's teammate (while the issue still carries the child's), `todo.status` completed (abandoned when closed as wontfix) and no subagent key, so the lead can still retire the item from a new plan. A closed item still marked by a child (one killed after closing, or one of another session) is returned to the lead the same way the next time a plan operation touches it, as long as the lead's actor owns it; `start` or appending it again then reopens it. The lead keeps no records of its children, so it does this even while the child that closed the item is still running. An open item held by a child is still refused. The record lives in the child's session branch, so a resumed child keeps its assignment. A child resumed after its run ended goes on with that record: an open issue is assigned to it again, a closed one stays closed, and its next report is posted on the issue as a follow-up; an untracked child's next report goes on its mission. A child's name, which its binding, report and hand-back messages use, is its session name as typed (`pi --name WordCounter` gives `WordCounter`), else a slug of what it was matched to: the plan item's text without a ticket prefix (`Write wordcount.py` gives `write-wordcount.py`) or the title of a ticket outside the plan, else `pi-` and the end of its session id (`pi-ff1c15`); each is cut at 40 characters. Its teammate is that name, cleaned, plus a six-character hash of the lead and child sessions (`wordcounter-0c2d7b`), so two children of the same name stay distinct; `pi.subagent_id` keeps the session id. A `KATA_TEAMMATE` the lead set for the child is kept. A child started without `--model`, `--models` or `--provider` switches to the parent's provider and model (and thinking level, unless `--thinking` is given). Revision guards prevent two children from taking the same task. Main todo mutations cannot complete delegated tasks: the child closes itself and `view` reloads Kata state. Saved child bindings retain identity when resumed. Child shutdown has a 3 s budget for the rollback, hand-back, mission or reports above. A `reload` is not an ending and changes nothing.

The main process retains `KATA_REF` and its explicit plan binding. Kata 0.21's native adapter owns session attention, uses `KATA_ATTENTION_HOST` to keep child sessions off the lead's attention, and skips OMP hosts. A hook generated by an older Kata lacks that guard; rerun `kata agent-hook install pi --attention` after upgrading Kata. The plugin leaves native attention baselines alone. A child still clears the inherited lead `KATA_REF` so its own assigned issue takes precedence. Use the qualified ref of its assignment for child scripts rather than assuming inherited `KATA_REF`. The native registry controls [contract coexistence](../how-to/use-with-kata-agent-hooks.md); children always receive their own assignment, and their contract in a folder with `.kata.toml`. `KATA_CONTRACT_SOURCE` replaces the contract the plugin injects, as on [omp](oh-my-pi.md#hooks); where Kata's native pi adapter covers the folder, the plugin injects no contract and the variable has no effect. The session keeps the contract it first gets, the built-in one included: start a new session after editing the file or correcting its path.

The plugin's `todo` tool supports `init`, `append`, `start`, `block`, `unblock`, `done`, `drop`, `rm` and `view`; `/todo` supports `start`, `done`, `drop`, `rm`, `append`, `block`, `unblock` and `takeover` (start a task another session holds, taking it over; see [closing rules](closing-rules.md)), and with no subcommand shows the plan. `done` takes the message and evidence the closing rules require and closes the task; an explicit `/todo done` records the user's completion attestation as external evidence. `init` accepts `ref` (the issue the plan serves), and refuses a new list that leaves out open tasks unless it passes `replace: true`, which closes them as wontfix. A held task is taken over with `takeover: true`. Where the plan lives (`KATA_DEFAULT_PROJECT` with a repo label, else the inferred project) and the lazy session parent follow the [OMP reference](oh-my-pi.md#where-the-plan-lives). After a Kata outage the plan replays into Kata; a task completed offline replays as closed only if it carries evidence and a 40-character message, otherwise it replays blocked so you can add evidence. Session-local plans (kept only while Kata is unreachable) and pending close retries persist in session custom entries and resume with the saved session. Children manage their own issues instead of mutating the main todo plan. Automatic parents reconcile from actual Kata children and accepted close evidence; explicit parents remain the lead's responsibility. A child started before its lead had a plan makes the session's automatic parent itself; a lead that ends with no plan of its own binds that parent first, so a parent holding only the child's mission closes. See [closing rules](closing-rules.md) and [limits](../explanation/limits.md).

Typing `#` plus part of a ticket id or title word in the interactive editor offers matching open Kata issues beside Pi's own items; accepting inserts the qualified ref (`kata-plugin#bc7q `). Behavior, scoping (`#<project>#<token>`, `KATA_DEFAULT_PROJECT`, digits-only tokens left alone) and the never-block-typing rule match the [OMP reference](oh-my-pi.md#ticket-references-in-the-prompt). Pi receives `#` as an added trigger character; only the interactive main session registers it.

Items that name a ticket (`<project>#<short_id>: <action>`) work that existing ticket instead of creating an issue. The ref must resolve with `kata show`, be open and be claimable by this session; otherwise the call fails and creates nothing. `start` claims the ticket if unowned and sets `todo.status=in_progress` (never `todo.phase`); `block` sets `work.attention` as for other items. `done` comments on the ticket (item, message, evidence), and the last open item naming a ticket closes it with that item's evidence exactly once. If Kata refuses that close because the ticket has open children, the item still completes, one comment says how many children block it, and the plugin retries the close after later todo operations and at shutdown once the children are closed. `drop` and `rm` only comment; a ticket is never closed as wontfix or reopened. A plan whose items all name tickets creates no session parent until an item without a ref needs an issue. Pi child processes do not bind such items: a child still follows the matching rules above.

The inbox is read per turn only: `kata inbox --for <address> --json` runs before each prompt, request text in the section is written with `&`, `<` and `>` as `&amp;`, `&lt;` and `&gt;` so it cannot close `<kata_inbox>`, and a request sent while the agent is idle or mid-run waits for the next prompt. Live delivery from `kata events --tail` is OMP-only, because Pi's `sendUserMessage` has `steer` and `followUp` but no delivery that starts a turn when idle and joins a running one at a step boundary without interrupting its tools. Under Kata's native pi adapter (`kata agent-hook install pi --attention`) this plugin skips the inbox read and Kata inserts the inbox itself, so neither the own-actor sender filter nor the escaping of request text applies.
