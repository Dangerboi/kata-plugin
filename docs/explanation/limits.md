# Limits

The plugins track todo plans, OMP delegates and inherited Pi child processes. Kata's accepted close records determine completion. Session-local todo plans (kept only while Kata is unreachable) and pending close retries are saved in harness session entries and restored on resume.

- **Delegate discovery — host API.** OMP matches a delegation to a plan task by name, ref or word overlap, and to the active task only for an explicit current-task handoff; Pi does the same after inheriting `KATA_PI_PARENT`. Pi does not expose a general child-process spawn/join hook. Processes launched with a replaced environment, from another machine, or before parent startup finishes must receive an explicit binding. **Upstream ask:** provide stable child identity, environment handoff, and lifecycle receipts.
- **OMP native harness — Kata CLI.** Kata has no omp harness: `agent-hook contract omp` and `attention-native omp` are rejected, and `agent-hook install` has no omp target. The omp plugin passes `pi` to `attention-native`, which only selects payload parsing and the session token. **Upstream ask:** an `omp` harness for `attention-native`, `status` and `install` (user scope `~/.omp/agent/extensions/`).
- **Close transcripts — Kata config.** The plugin does not read Kata's config, so `[close.transcript] enabled = false` there does not stop omp and pi sessions from recording a session on a close. To opt out, set `KATA_CLOSE_TRANSCRIPT_ENABLED=false` in the launching environment ([Record agent sessions on closes](../how-to/record-session-transcripts.md)). A harness launched from the `bash` tool inherits the switch and the pair, so its closes link the launching session.
- **Shell attribution — by design.** Recognized standalone Kata commands receive the delegate's teammate; actor impersonation with `--as` is refused. Dynamic aliases and opaque embedded scripts must use the supplied binding command themselves. Lexical rewriting is not a security sandbox.
- **Observation and proof — host API / by design.** Tool observations cannot audit opaque programs' filesystem side effects. Missing receipts, unknown writes, failed checks, or incomplete reports can leave finished work open for review. Idle alone is not completion. **Upstream ask:** provide authoritative write-path and terminal verification receipts for opaque tools and delegated writers.
- **Session retention — host API / by design.** Durable OMP/Pi state requires a saved session and its custom entries; ephemeral sessions, deleted session files, or host compaction that discards those entries cannot restore local plans or retry queues. **Upstream ask:** preserve extension state across compaction and provide a larger durable state store with retention guarantees.
- **Outages and concurrent writes — Kata CLI.** Foreground hooks have bounded budgets. Outages are quiet and retryable, not proof that tracking succeeded. Guarded multi-key attention updates can partially succeed before a conflict; reopen has no atomic CLI guard. **Upstream ask:** add atomic multi-key metadata updates, and revision-guarded reopen. Existing ownership/revision checks preserve conflicting writers' changes.
- **Session ownership — host API / Kata CLI.** A started plan item belongs to the lead session that started it ([closing rules](../reference/closing-rules.md)), which releases it when it ends gracefully. A session that crashed, was killed, or ran out of omp's shutdown budget before the release keeps its items, and the plugin cannot tell whether it still runs, so they stay refused to other sessions until one takes them over on request. The marker is plain metadata: anyone who runs `kata meta set` with the same actor can move it, and a pi child only knows its lead's own session, not the sessions that lead was forked from. **Upstream ask:** session liveness (a lock or heartbeat) the plugin can read.
- **Abrupt termination — host API.** Graceful child shutdown can mark unfinished work for review; a crash or SIGKILL cannot run shutdown hooks. Saved retries resume when the harness session is reopened, rather than through an always-running background worker. omp's delegate cleanups work the same way: the lead's saved state keeps every delegate not yet handed back or rolled back, and reopening the lead session finishes them (a delegate that was still running then counts as aborted). omp has no session lock and the plugin cannot tell whether the omp that held the session has exited, so resume a lead session only after that omp has exited; a second omp on the same session file would treat the first one's running delegates as aborted and hand back or roll back work in progress. A session that is never reopened still leaves them. **Upstream ask:** provide durable lifecycle delivery or launcher cleanup for terminated sessions.
- **Shutdown budget — host API.** omp gives each extension's `session_shutdown` handler 2 s, then exits. Whatever the plugin still has queued then is cut off: delegate hand backs and rollbacks (about ten Kata calls each), pending closes, and the automatic parent's close (six or more). The plugin's own 10 s shutdown bound does not extend omp's; pi has no limit of its own and waits for it. The end of each lead turn waits up to 15 s for exited delegates to be handed back or rolled back, so cleanups that finish while the session keeps running are written before the turn ends. Still cut off: `/exit` or Ctrl+C while delegates run or exit, and a crash or SIGKILL. A cut-off delegate cleanup is saved with the lead session and finished in the background when that session is resumed, like pending closes; until then the task stays on the delegate's teammate with nobody told, and a session that is never resumed leaves it so. **Upstream ask:** a longer or extension-requested shutdown budget.
- **Inbox sender — Kata daemon.** The session inbox shows only requests whose `from` equals the session's own actor, but on a daemon without authentication `from` is whatever actor the writer claims, so the filter stops other people's requests, not a writer who impersonates the actor. Kata also keeps one request per issue and recipient, so another writer's request on the same issue replaces yours, and the session then sees neither. Under Kata's native pi adapter (`kata agent-hook install pi --attention`) Kata inserts the inbox itself, so this filter does not apply there. Run the daemon with authentication if other writers share the store. **Upstream ask:** a sender identity the daemon verifies.
