# Limits

The plugins track todo plans, OMP delegates, OpenCode todo plans and subagents, Claude Code todo plans and agents, and inherited Pi child processes. Kata's accepted close records determine completion. Session-local todo plans (kept only while Kata is unreachable) and pending close retries are saved in harness session entries and restored on resume (OpenCode keeps them in its per-plugin storage, Claude Code in its plugin store; see [Claude Code](#claude-code)).

- **Delegate discovery — host API.** OMP binds a delegation to a plan task only when its text names the task (title, ref, or a ticket item's ticket ref); a spawn that only describes the work is untracked, and its run is recorded as a mission. Pi does the same after inheriting `KATA_PI_PARENT`. Pi does not expose a general child-process spawn/join hook. Processes launched with a replaced environment, from another machine, or before parent startup finishes must receive an explicit binding. **Upstream ask:** provide stable child identity, environment handoff, and lifecycle receipts.
- **Delegate inbox on a revived delegate — host API.** An OMP delegate reads its inbox when its `before_agent_start` hook runs, and OMP skips that hook when it revives a parked delegate (a follow-up message to an idle one), so a request sent after the delegate's last prompt shows only on a turn where the hook runs. The delegate's note names its inbox address, but a request sent before the delegate first starts needs that address in advance. **Upstream ask:** run `before_agent_start` for a revived delegate, or give it a per-turn context hook.
- **Missions — by design.** A mission records an untracked delegate's run, not proof of what it did: it closes as `audit-no-change`, and any change the run made (through `bash` or edits) is the lead's to verify. It is made when the delegate exits with a report. A lead saves no record of an untracked delegate before its mission exists, so one that crashes or is killed between that exit and its settle never makes the mission. With Kata's `[close.throttle]` on, a burst of more than three sibling closes in a minute is refused; a lead retries a mission close refused that way 60 seconds later. The mission is saved with the lead's state as soon as it is created, so a lead that ends or is killed before that close finishes it when its session is resumed. A mission left open (a pi child whose close was throttled or cut off by its 3 s shutdown budget, a lead that is never resumed) is closed by the automatic parent's audit once nothing else under the parent is open; one under an explicit parent stays open for the lead to close.
- **OMP native harness — Kata CLI.** Kata has no omp harness: `agent-hook contract omp` and `attention-native omp` are rejected, and `agent-hook install` has no omp target. The omp plugin passes `pi` to `attention-native`, which only selects payload parsing and the session token. **Upstream ask:** an `omp` harness for `attention-native`, `status` and `install` (user scope `~/.omp/agent/extensions/`).
- **OMP todo guard — host API.** omp runs the `tool_call` handlers of every call in one assistant message before any of those calls executes. A `kata close` and a `todo done` sent in the same message therefore get the done refused, because the close has not run yet; the agent calls done again on its next turn. Likewise `todo drop X` and an `init` without `X` in one message get the init refused. An `init` that leaves out tasks omp never held (an open child of an adopted parent, of `KATA_REF` or of a claimed ticket) is refused with advice to keep them in the list, or `append` them and then `drop` them; one that leaves out tasks omp did hold is refused with advice to `drop` them first. The guard waits up to 10 seconds for Kata and lets the call through when Kata is slower or unreachable. **Upstream ask:** run a message's calls in order, each after the previous one's `tool_call` and execution.
- **OMP todo mirror — host API.** The mirror sees the whole list only after omp has saved it, so the user's `/todo` edits and RPC `set_todos` cannot be refused, only mirrored: a task they mark completed while its issue is open stays open, labeled `needs-review`. Tasks are matched by text, so a task moved to another phase in omp keeps its phase in Kata. omp removed the `blocked` status in 18.20.0, so a wait is recorded with `kata comment` rather than in the plan. omp gives the backend 30 s per list and may send the next list before the last one has landed in Kata; when Kata is that slow and the user moves with `/tree` or forks meanwhile, a list can be compared against an older one and a change repeated, which can undo a change made to the same task in Kata in that window. The plugin leaves omp's backend setting to the user: until Kata is picked under `/settings` → Tools → Todos → Todo Backend, nothing reaches Kata.
- **Close transcripts — Kata config.** The plugin does not read Kata's config, so `[close.transcript] enabled = false` there does not stop omp, pi, OpenCode and Claude Code sessions from recording a session on a close. To opt out, set `KATA_CLOSE_TRANSCRIPT_ENABLED=false` in the launching environment ([Record agent sessions on closes](../how-to/record-session-transcripts.md)). A harness launched from the `bash` tool inherits the switch and the pair, so its closes link the launching session.
- **OpenCode environment — host API.** A variable set in the shell that starts an OpenCode client reaches the plugin only with `--standalone`. The default background service, and any client attached to it, runs with the service's own environment, so `KATA_REF`, `KATA_DEFAULT_PROJECT`, `KATA_AUTHOR`, `KATA_TEAMMATE`, `KATA_OPENCODE_EXECUTABLE` and `KATA_CLOSE_TRANSCRIPT_ENABLED` set at launch are not seen. Use plugin options in `opencode.json` (the close switch has no option and comes from the server's environment).
- **OpenCode todo display — host API.** The sidebar shows the list the model sent, which OpenCode saves before the plugin runs and neither a hook nor the result can change. Kata wins by refusal: a call whose list disagrees with the plan is refused and the sidebar keeps the last list that matched. An item a delegate closed in Kata therefore shows as closed in the sidebar only after the lead's next `todowrite`. The plan section in the system prompt does not stop stale calls; the refusal does. A refused call's list never reaches Kata.
- **OpenCode settling — host API.** OpenCode has no event for the end of a session, and the plugin's cleanup also runs when an idle location is evicted while the session can still resume. Pending closes and delegate hand-backs are therefore settled at the end of each lead turn, not when the TUI exits; the automatic parent closes only on `session.deleted` or `session.archived`; and cleanup (eviction or server exit) drains what fits, saves the rest and closes or releases nothing. Work left pending finishes at the next plugin start for the session's folder. A session the user never deletes or archives leaves its automatic parent open.
- **OpenCode transcripts — host API.** A close records agent `opencode` and the session id. AgentsView may not open OpenCode v2 sessions yet, so the link on such a close may not resolve.
- **OpenCode follow-ups — by design.** A `subagent` call with `sessionID` stays on the delegate's record and issue. If the issue is still open, tracking resumes on it. If it is closed, the follow-up's report becomes a comment and the issue stays closed, because Kata has no revision-guarded reopen. A follow-up to an open issue whose delegate runs no tool is rolled back to where the issue was before the follow-up; its report is still posted. An untracked delegate (no plan item, no ticket) whose run became a mission is saved with it, so a follow-up's report goes on that mission, also after a restart; one that left no mission is not saved, and a follow-up to it after a restart is not tracked.
- **OpenCode shell display — host API.** The plugin rewrites Kata commands in the `shell` tool before they run; the TUI keeps showing the command the model wrote. `shell` is excluded from Code Mode, so Code Mode calls do not bypass the rewrite.
- **Kata refs in files — by design.** The ref guard reads the text a tool call adds, so it catches the refs the session knows (its plan, claims, assignment and delegates) in `write`, `edit`, patch, `ast_edit` and `git commit` calls. The guard reads omp's hashline, apply_patch and sloppy patch formats; an unusual patch syntax it does not parse may get past it, because it is a hygiene check that lets a call through when it cannot read the call. A ref written by a script or another program, in a changed file the call does not show, in a commit made through `git` aliases or amended later, or a ref of an issue the session never touched, is not caught. A claim made in the shell and never adopted is kept for the session, its forks and its branch switches, but not across a resume in a new process, so a resumed session does not know it. A pi child process knows only its own assignment and the parent it was started under, not the lead's other plan items, because the two share no channel but the marker environment; an omp delegate on a worker thread asks the lead's thread and is unchecked against the lead's refs only when that answer takes over a second. The check waits 2 seconds and then lets the call through.
- **Shell attribution — host API / by design.** Recognized standalone Kata commands receive the delegate's teammate and the binding's workspace and project; actor impersonation with `--as` is refused. On omp, every `kata` the lead or a delegate launches through omp's bash tool, also from a script, a function, a nested shell or a pipeline it starts, goes through a shim the plugin puts first on `PATH` with `PI_SHELL_PREFIX`. The shim loads that agent's own author, teammate, inbox user and close transcript, so a `KATA_AUTHOR`, `KATA_TEAMMATE` or `KATA_INBOX_USER` the model sets or exports does not change who the call is attributed to. The lead's first prompt and each bash call wait at most 1.5 s for that agent's identity to be written, and the lead's read of a worker's actor is bounded the same way; the call then runs anyway, and a late write still lands. Until a write lands, or after one fails, `kata` uses the identity last written for that agent, or, if none was ever written, gets only the rewrite, as without the shim. The shim does not cover a call to the real `kata` by absolute path, a forged `PI_SESSION_ID`, a `PI_SHELL_PREFIX` of your own that puts another `kata` first on `PATH`, or the binding's workspace and project inside opaque scripts, and `--as` is refused only on recognized standalone commands: inside an opaque script an explicit `--as` or `--teammate` outranks the identity the shim loads. Opaque scripts and dynamic aliases must use the supplied binding command themselves. On native Windows, or where no temp directory allows executables, the plugin warns once and only rewrites commands, as it does on the other hosts. If an identity write on the lead's thread (the lead's or a main-thread delegate's) fails, or the lead's read of a worker's actor fails or takes over 1.5 s, the plugin warns once until a successful identity write resets the warning; a worker's own failed write, or a worker with no known lead, is only logged at debug. A removed shim directory needs an omp restart. The shim relies on omp running `PI_SHELL_PREFIX` before each command. Neither the shim nor the rewrite is a security sandbox.
- **Observation and proof — host API / by design.** Tool observations cannot audit opaque programs' filesystem side effects. Missing receipts, unknown writes, failed checks, or incomplete reports can leave finished work open for review. Idle alone is not completion. **Upstream ask:** provide authoritative write-path and terminal verification receipts for opaque tools and delegated writers.
- **Session retention — host API / by design.** Durable OMP/Pi state requires a saved session and its custom entries; ephemeral sessions, deleted session files, or host compaction that discards those entries cannot restore local plans or retry queues. **Upstream ask:** preserve extension state across compaction and provide a larger durable state store with retention guarantees.
- **Outages and concurrent writes — Kata CLI.** Foreground hooks have bounded budgets. Outages are quiet and retryable, not proof that tracking succeeded. Guarded multi-key attention updates can partially succeed before a conflict; reopen has no atomic CLI guard. **Upstream ask:** add atomic multi-key metadata updates, and revision-guarded reopen. Existing ownership/revision checks preserve conflicting writers' changes.
- **Session ownership — host API / Kata CLI.** A started plan task belongs to the lead session that started it ([closing rules](../reference/closing-rules.md)), which releases it when it ends gracefully. A session that crashed, was killed, or ran out of omp's shutdown budget before the release keeps its tasks, and the plugin cannot tell whether it still runs, so they stay refused to other sessions until one takes them over on request. The marker is plain metadata: anyone who runs `kata meta set` with the same actor can move it, and a pi child only knows its lead's own session, not the sessions that lead was forked from. **Upstream ask:** session liveness (a lock or heartbeat) the plugin can read.
- **Abrupt termination — host API.** Graceful child shutdown can mark unfinished work for review; a crash or SIGKILL cannot run shutdown hooks. Saved retries resume when the harness session is reopened, rather than through an always-running background worker. omp's delegate cleanups work the same way: the lead's saved state keeps every delegate not yet handed back or rolled back, and reopening the lead session finishes them (a delegate that was still running then counts as aborted). omp has no session lock and the plugin cannot tell whether the omp that held the session has exited, so resume a lead session only after that omp has exited; a second omp on the same session file would treat the first one's running delegates as aborted and hand back or roll back work in progress. A session that is never reopened still leaves them. **Upstream ask:** provide durable lifecycle delivery or launcher cleanup for terminated sessions.
- **Shutdown budget — host API.** omp gives each extension's `session_shutdown` handler 2 s, then exits. Whatever the plugin still has queued then is cut off: delegate hand backs and rollbacks (about ten Kata calls each), pending closes, and the automatic parent's close (six or more). The plugin's own 10 s shutdown bound does not extend omp's; pi has no limit of its own and waits for it. The end of each lead turn waits up to 15 s for exited delegates to be handed back or rolled back, so cleanups that finish while the session keeps running are written before the turn ends. Still cut off: `/exit` or Ctrl+C while delegates run or exit, and a crash or SIGKILL. A cut-off delegate cleanup is saved with the lead session and finished in the background when that session is resumed, like pending closes; until then the task stays on the delegate's teammate with nobody told, and a session that is never resumed leaves it so. **Upstream ask:** a longer or extension-requested shutdown budget.
- **Inbox sender — Kata daemon.** The session inbox shows only requests whose `from` equals the session's own actor, but on a daemon without authentication `from` is whatever actor the writer claims, so the filter stops other people's requests, not a writer who impersonates the actor. Kata also keeps one request per issue and recipient, so another writer's request on the same issue replaces yours, and the session then sees neither. Under Kata's native pi adapter (`kata agent-hook install pi --attention`) Kata inserts the inbox itself, so neither this filter nor the escaping of request text applies there. The same holds on Claude Code's default inbox path (`kata agent-hook install claude` with the plugin's `contract` option off), where Kata writes the section. Run the daemon with authentication if other writers share the store. **Upstream ask:** a sender identity the daemon verifies.

## Claude Code

The limits above that name no host apply to the Claude Code plugin too. These are its own. Tested with Claude Code 2.1.332.

- **Mod API — host API.** Claude Code's mod API is early access and may change between releases without notice, so a new Claude Code release can stop the plugin from loading or change what its hooks see until the plugin follows. `bun run validate:claude`, `bun run test:claude` and `bun run smoke:claude` ([development](../development.md#smoke-test-against-a-real-claude-code)) check a new release. **Upstream ask:** a stable mod API.
- **Saved state — host API.** `$.store`, where the plugin keeps a session's plan state, delegate records and pending closes, is one 4 MiB file shared by every session and every mod on the machine, and a read-then-write of a key is not atomic: two Claude Code processes saving at the same moment can lose one of the two writes. The plugin gives each session a key of its own, so only that session ever writes it, and saves it again after every change: a record lost to such a race comes back with that session's next save, but one lost just before its session ends or is killed is gone, and the work it recorded is not finished at a resume. The plugin drops an ended session's record after 7 days and any record untouched for 30 days, and when its records pass 2 MiB it drops the oldest ended sessions, those that owe nothing first. A session left unresumed past those limits loses a retry queue it still owed or a plan it left open (an ended session that left a task open or owes closes is kept 30 days, any other 7, unless the records pass 2 MiB). Records of other mods count against the same 4 MiB.
- **Session end — host API.** The whole chain of `session.end` hooks has 1.5 s. The plugin's shutdown gets at most 1.2 s of it, and the plugin then saves the session's record: the automatic parent's close (six or more Kata calls), delegate hand backs and pending closes that do not fit stay in the saved record and finish when the session is resumed with `claude --resume`. A session that is never resumed leaves them undone. `/clear` and `/resume` end nothing, so the switch settles the old session instead.
- **Fork, resume and clear — host API.** These fire no `session.start`. The plugin finds a new session id at its next hook and switches, and a fork shares its source's plan only when Claude Code's `classic.SessionStart` hook runs. Under a managed-settings guard it does not (next item), so a fork there starts from a plan of its own. `claude --resume <id> --fork-session` is a fork too, but Claude Code names the source to the mod nowhere (the new session starts with its own id), so that fork starts from a plan of its own as well. **Upstream ask:** the source session's id in `session.start`. Work an old session left open is finished when that session is resumed; the plugin does not finish other sessions' saved work at start, as OpenCode does.
- **Managed-settings guard — host API.** Where Claude Code loads its built-in guard (a machine with managed settings or `managed-mcp.json`, or a Team or Enterprise login), it skips a mod's `classic.*` hooks, `session.compact` and `prompt.*` hooks. The plugin's `classic.SessionStart` (fork detection, session switches before the next hook) and `classic.Stop` (the reminder that keeps the model working while tasks are open) are among them: forks do not share the source plan there, and a model that stops with open tasks gets no reminder (the turn's settle still runs). The plan sent after compaction is not refreshed under the guard.
- **Subagents the plugin cannot see — host API.** Code Review workflows (a placeholder prompt, and a rewrite of their input is ignored) are untracked: they get no issue and no mission. A Workflow agent the engine restarts after a stall (a retry) raises no spawn, so the retry runs under an agent id the plugin has no record of and is untracked; its `kata` commands then run under the teammate a record would give it. A resumed run can only be refused or left alone; the plugin never rewrites its prompt.
- **Slow assignment — host API.** A spawn hook has 10 s in all. The plugin's waits for the assignment (those before Claude Code's own spawn, and one after it) share it: the waits before the spawn share 7 s and keep 3 s for Claude Code's own spawn, and the wait after keeps 0.5 s for the hook's return. The agent starts without its assignment when Kata is slower: it learns of its issue from its first `todo` call.
- **Hot reload — host API.** A hot reload of the mod in an interactive session (a saved change to a watched plugin folder, `/reload-plugins`, a changed option) loses the in-memory delegate records and starts a fresh module. Its session start restores the delegates from the session's saved record the way a resume does: a delegate still running counts as aborted and its issue is handed back for review, so that agent's next `todo` call fails with `its issue was handed back` (its `kata` commands still run under its teammate).
- **Shell rewrite under auto mode — host API.** Auto permission mode refuses a tool call a hook changed after the classifier read it. In auto mode the plugin therefore denies a delegate's `kata` command that needs `--teammate`, and a `kata close` of the lead or a delegate that lacks the session pair, and names the exact command to run; the model's next call carries the change. This costs one extra tool call per such command. There is no settings-hook fallback, and the teammate-id case of a command running under a teammate agent has not been run against a real Claude Code.
- **`contract` option off by default — by design.** `kata agent-hook install claude` owns the contract, the inbox and session attention, so the plugin adds the contract and inbox sections only when its `contract` option is on. Without Kata's hook and without that option, the model gets no contract.
- **Live inbox delivery — host API.** Claude Code has no event for an idle session, so the plugin reads whether the main loop works from `turn.start` and `turn.complete`. A request that arrives mid-turn is appended to the conversation and reaches the model with its next request, never between a tool call and its result; one appended in a turn's final step rides the next turn. After the person presses Stop, delivery is refused until they type again. A request that arrives as the process exits can be lost. In `claude -p` each delivery uses a turn of `--max-turns`, and nothing is delivered after the run ends. The live follower can be turned off with the `liveInbox` option or `KATA_CLAUDE_LIVE_INBOX=0`.
- **Headless runs — host API.** `claude -p` and the Agent SDK run the plugin's hooks and draw nothing, so the plan band, card, `#` completion and `/todo` exist only in an interactive session, and `--plugin-dir` folders are not watched there.
